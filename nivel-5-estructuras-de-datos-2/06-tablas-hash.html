Tablas hash

Buscar por nombre sin recorrer nada: calcular dónde está. ~35 minutos.

Al terminar podrás: escribir una clase TablaHash que guarda pares clave-valor en cubetas, resuelve las colisiones con listas y se agranda sola (rehash) cuando se llena; y explicar por qué std::unordered_map busca en O(1) en promedio pero O(n) en el peor caso.

Antes de empezar: repite sin mirar el quiz de la lección 5.5 (ordenamiento). Recordar lo de ayer es lo que hace que se quede.

Por qué. Un árbol balanceado (lección 5.3) encuentra una clave en O(log n). Una tabla hash lo hace, en promedio, en O(1): da igual que tenga diez claves o un millón. Por eso está en todas partes: diccionarios, cachés, bases de datos, el unordered_map que usaste en la lección 4.2. Y es pregunta fija de examen: colisiones, factor de carga y peor caso.

1. La idea: calcular el sitio en vez de buscarlo

Piensa en los casilleros de un gimnasio, numerados del 0 al 7. Si la regla fuera «tu casillero es el número que sale de tu nombre», no tendrías que abrirlos todos para encontrar tus cosas: calculas el número y vas directo.

Una tabla hash es eso:

  • Un vector de cubetas (los casilleros). En inglés, buckets.
  • Una función hash que convierte la clave (por ejemplo, un string) en un número.
  • El índice de la cubeta es ese número módulo el número de cubetas: hash(clave) % m.

Buscar es: calcular el índice (rápido) y mirar solo esa cubeta (Stanford CS106B, Hashing).

2. La función hash

Convierte una clave en un número. La que usamos en el curso multiplica por 31 y suma cada letra:

size_t hashCadena(const string& clave) {
    size_t h = 0;
    for (char c : clave) h = h * 31 + (unsigned char)c;   // mezcla cada letra
    return h;
}

cout << hashCadena("ana");       // 96724
cout << hashCadena("ana") % 8;   // 4  → con 8 cubetas, "ana" va a la cubeta 4

Lo que se le pide a una buena función hash:

  • Determinista: la misma clave da siempre el mismo número. Si no, nunca la encontrarías.
  • Reparte bien: claves parecidas deben caer en cubetas distintas.
  • Rápida: si calcular el hash cuesta mucho, se pierde la ventaja.

¿Por qué no sumar las letras y ya? Porque "amor" y "roma" tienen las mismas letras y darían el mismo número. Multiplicar por 31 en cada paso hace que el orden cuente: hashCadena("amor") vale 2998031 y hashCadena("roma") vale 3506321.

Error típico: un hash con signo. Si guardas el hash en un int, al crecer se desborda (comportamiento indefinido) y puede salir negativo; y un número negativo % m da un índice negativo: cubetas[-3] lee memoria ajena. Usa size_t, que no tiene signo.

3. Colisiones: dos claves, la misma cubeta

Hay infinitas claves posibles y pocas cubetas, así que tarde o temprano dos claves caen en el mismo sitio. Eso es una colisión, y no es un error: es normal.

La solución más común es el encadenamiento (chaining): cada cubeta no guarda un par, sino una lista de pares. Si dos claves chocan, las dos viven en la misma lista.

class TablaHash {
private:
    vector<list<pair<string, int>>> cubetas;   // cada cubeta: lista de (clave, valor)
    size_t cantidad;                           // pares guardados en total

    size_t indiceDe(const string& clave) const {
        return hashCadena(clave) % cubetas.size();
    }
public:
    TablaHash(size_t m = 8) : cubetas(m), cantidad(0) {}
    // insertar, buscar, eliminar, factorDeCarga, rehash: abajo
};

4. Insertar, buscar y eliminar

Las tres operaciones empiezan igual: calcular la cubeta. Después, todo es recorrer una lista corta, como en el Nivel 3.

void insertar(const string& clave, int valor) {
    auto& cubeta = cubetas[indiceDe(clave)];
    for (auto& par : cubeta)
        if (par.first == clave) { par.second = valor; return; }   // ya estaba: actualizar
    cubeta.push_back({clave, valor});                             // nueva: al final
    cantidad++;
    if (factorDeCarga() > 1.0) rehash(cubetas.size() * 2);        // sección 5
}

bool buscar(const string& clave, int& valor) const {
    for (const auto& par : cubetas[indiceDe(clave)])
        if (par.first == clave) { valor = par.second; return true; }
    return false;
}

eliminar es el mismo recorrido con un iterador, para poder llamar a cubeta.erase(it) y bajar cantidad. Lo escribes tú en el miniproyecto.

5. Factor de carga y rehash

Si metes 1000 claves en 8 cubetas, cada lista tendrá unas 125: buscar ya no es rápido. Lo que importa es cuántos pares hay por cubeta:

factor de carga = pares / cubetas      // α («alfa») = n / m

Cuando el factor pasa de un límite (en el curso, 1.0), la tabla hace un rehash: pide el doble de cubetas y vuelve a calcular la cubeta de cada clave, porque el índice depende de m. Con 4 cubetas, al insertar el quinto par (α = 5/4 = 1.25) toca mudarse a 8:

Se recalcula hashCadena(clave) % 8 para cada par. En color, los que cambiaron de cubeta:

Fíjate en ana: con 4 cubetas iba a la 0 (96724 % 4); con 8, va a la 4 (96724 % 8). Cada par se reparte de nuevo y las listas quedan cortas otra vez.

void rehash(size_t nuevas) {
    vector<list<pair<string, int>>> viejas(nuevas);
    viejas.swap(cubetas);                     // cubetas: tamaño nuevo y vacía
    for (auto& cubeta : viejas)
        for (auto& par : cubeta)
            cubetas[indiceDe(par.first)].push_back(par);   // índice con el m NUEVO
}                                             // «viejas» se destruye sola

Un rehash cuesta O(n), porque mueve todo. Pero como cada vez se duplica, pasa pocas veces: repartido entre todas las inserciones, insertar sigue costando O(1) en promedio. Es el mismo truco que usa vector al crecer (lección 1.8).

Error típico: copiar las cubetas tal cual. Si en el rehash haces nuevas[i] = cubetas[i], ana se queda en la cubeta 0. Pero buscar("ana") ahora calcula 96724 % 8 = 4, mira la cubeta 4 y no la encuentra. La clave sigue en memoria, pero es como si no existiera. Hay que recalcular el índice de cada par.

6. ¿Cuánto cuesta? Promedio y peor caso

Con una buena función hash y el factor de carga bajo control, cada lista tiene, en promedio, uno o dos pares. Por eso insertar, buscar y eliminar son O(1) en promedio.

El peor caso es otra historia. Si todas las claves caen en la misma cubeta (una función hash mala, o datos preparados para atacarla), la tabla se convierte en una sola lista y buscar es O(n). El ejemplo extremo:

size_t hashMalo(const string& clave) { return 0; }   // ¡todas a la cubeta 0!

cppreference lo dice así para unordered_map::find: «constante en promedio, lineal en el peor caso» (cppreference, find).

7. std::unordered_map y std::hash

En la práctica no escribes tu tabla: usas std::unordered_map, que por dentro es exactamente esto, cubetas con elementos agrupados por su hash (cppreference, std::unordered_map). Hasta te deja mirar las cubetas:

#include <unordered_map>

unordered_map<string, int> cuenta;
for (string p : {"uno", "dos", "uno"}) cuenta[p]++;   // [] crea con 0 si no existe

cout << cuenta["uno"];           // 2
cout << cuenta.size();           // 2   (claves distintas)
cout << cuenta.bucket_count();   // cuántas cubetas tiene (con g++, 13)
cout << cuenta.load_factor();    // size / bucket_count
cout << cuenta.max_load_factor();// el límite antes del rehash: 1 al empezar

La función hash que usa es std::hash<Clave>, que ya existe para int, string, double, apuntadores… (cppreference, std::hash):

size_t h = hash<string>{}("ana");   // un número grande; cuál, depende del compilador

Si la clave es una clase tuya, unordered_map no sabe calcular su hash y no compila: hay que darle uno. map (un árbol, lección 5.3) solo necesita <.

Error típico: contar con el orden de recorrido. Recorrer un unordered_map sigue el orden de las cubetas, no el de inserción ni el alfabético. Puede cambiar con un rehash o con otro compilador. Si necesitas orden, usa map o copia las claves a un vector y ordénalo (lección 5.5).

¿Qué pasa en la memoria?

Tu TablaHash t; en main vive en la memoria automática (la pila de llamadas o stack) y es pequeña: el objeto vector y cantidad. Las cubetas están en el montón (heap), en un bloque contiguo: cada una es un objeto list vacío o casi, de unos pocos apuntadores (míralo con sizeof). Los pares, en cambio, viven en los nodos de esas listas, cada uno pedido por separado y disperso por el montón.

Las direcciones son inventadas: lo que importa es que las cubetas van seguidas y los nodos no.

Un rehash es una mudanza: se pide un bloque nuevo de cubetas el doble de grande, se reparten los pares y el bloque viejo se libera solo al destruirse viejas (nadie escribe delete: vector y list son los dueños). std::unordered_map es más fino: no muda los elementos, por eso un rehash invalida los iteradores, pero las referencias y apuntadores a los elementos siguen valiendo (lo dice cppreference en «Iterator invalidation»).
