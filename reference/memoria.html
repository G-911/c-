1. Las 4 zonas de la memoria

Un programa en ejecución usa cuatro zonas. La zona de código guarda las instrucciones (tus funciones y métodos). La memoria estática guarda las variables globales y las static: viven todo el programa. La memoria automática (la pila de llamadas o stack) guarda los parámetros y variables locales de cada función. El montón (heap) guarda lo que pides con new, y vive hasta que haces delete.

int* p = new int(42);   // p vive en el marco de main; el 42, en el montón

El dibujo es un modelo mental: el orden real de las zonas depende del sistema. Una plantilla tampoco ocupa memoria por sí misma: el compilador genera una versión por cada tipo que usas, y esas versiones van a la zona de código.

2. Memoria automática (la pila de llamadas)

Cada vez que llamas a una función se apila un marco: el espacio con sus parámetros y sus variables locales. Al hacer return, el marco se libera solo; no tienes que hacer nada. Cada variable es una caja de sizeof(tipo) bytes (un int ocupa normalmente 4). Los valores intermedios de una operación (a + b) son temporales que también se liberan solos.

marco de cuadrado
n = 5
marco de main
x = 5
r = ?

Arriba, el marco más reciente: es el primero en irse.

La pila de llamadas es pequeña. En la práctica suele ser de 1 MB (Visual Studio en Windows) a unos 8 MB (g++/Clang en Linux). Una recursión demasiado profunda o un arreglo local enorme la llenan: desbordamiento de pila (stack overflow) y el programa se cae. No la confundas con la clase Pila del Nivel 3: comparten nombre, no son lo mismo.

3. Ámbito y tiempo de vida

Son dos cosas distintas. El ámbito es dónde puedes usar el nombre. El tiempo de vida es cuándo existe el objeto en memoria. Una variable local nace al declararla y muere al cerrar su bloque {}; si está dentro del cuerpo de un bucle, nace y muere en cada vuelta. Una global o una static vive todo el programa, aunque su nombre solo se vea en su bloque.

VariableÁmbito (nombre)Tiempo de vida (objeto)
localsu bloquehasta cerrar su bloque
static localsu bloquetodo el programa
globaltodo el archivotodo el programa
con new— (se usa por apuntador)hasta delete
int contar() {
    static int veces = 0;   // se crea una sola vez y conserva su valor
    return ++veces;
}

Una lambda que captura por referencia ([&]) queda colgante si vive más que las variables que capturó. Capturar por copia ([=]) guarda copias dentro de la lambda.

4. Copias: paso por valor

Pasar por valor crea una copia en el marco de la función: cambiarla no toca tu variable. Copiar un int es gratis; copiar un string o un vector grande copia todos sus datos, y eso cuesta. Un operador como + devuelve un objeto nuevo (temporal); = copia dentro de un objeto que ya existe.

void f(std::vector<int> v);          // copia el vector entero
void g(const std::vector<int>& v);   // no copia: solo lee el original

Fraccion c = a + b;   // + crea un objeto nuevo
c = a;                // = copia a dentro de c, que ya existía

Fuente: LearnCpp — Pass by lvalue reference

5. Referencias

Una referencia es otro nombre para la misma caja. En el modelo mental no ocupa una caja nueva ni copia nada (el compilador puede usar una dirección por dentro, pero tú no la ves). Úsala para que una función modifique tu variable (int&) o para leer algo grande sin copiarlo (const T&).

x · r
7
0x100
int x = 7;
int& r = x;   // r es x con otro nombre: r = 9 cambia x

Nunca devuelvas una referencia a una variable local: el marco se libera al salir y la referencia queda colgante.

6. Apuntadores

Un apuntador es una variable normal (su propia caja) que guarda una dirección. Puede apuntar a la memoria automática o al montón. nullptr significa «no apunta a nada». Un apuntador colgante guarda la dirección de algo que ya murió: usarlo es comportamiento indefinido.

x
5
0x100
p
0x100
0x108 · apunta a x
int* p = &x;     // p guarda la dirección de x
p = nullptr;     // ya no apunta a nada

7. El montón: new y delete

new reserva en el montón y devuelve la dirección; eso vive hasta que alguien haga delete. Ese alguien es el dueño: siempre debe estar claro quién es. Cada new se empareja con un delete, y cada new[] con un delete[].

ErrorQué pasa
fuga de memoriapierdes la dirección sin delete: esa memoria queda ocupada hasta que el programa termina
apuntador colganteusas la dirección después del delete
doble liberacióndos dueños hacen delete de lo mismo (típico de la copia superficial)
Nodo* borrar = actual->sig;
actual->sig = borrar->sig;   // 1.º reengancha
delete borrar;               // 2.º libera
borrar = nullptr;            // 3.º que no quede colgante

Copia superficial: se copia solo el apuntador → dos dueños del mismo montón → doble liberación. Copia profunda: se crean nodos nuevos con los mismos valores.

8. Objetos en memoria

Un objeto son sus atributos juntos en un bloque. Los métodos no se copian en cada objeto: hay uno solo, en la zona de código. El constructor marca el nacimiento y el destructor la muerte. Un objeto local vive en la memoria automática; uno creado con new, en el montón hasta delete.

Un objeto derivado lleva dentro su parte base. Orden: se construye primero la base y luego la derivada; se destruye al revés.

Perro p
[ parte Animal: nombre ]
[ parte Perro: raza ]
Perro p;   // Animal() → Perro() ... al morir: ~Perro() → ~Animal()
Animal a = p;   // slicing: se copia solo la parte Animal; la raza se pierde

Por eso los objetos polimórficos se manejan por apuntador o referencia, y la base necesita destructor virtual para que delete de un Animal* libere también la parte derivada. En la práctica, cada objeto de una clase con métodos virtual lleva además un apuntador oculto a una tabla de funciones (la vtable); el estándar no lo exige, pero así lo hacen los compiladores normalmente.

9. Estructuras de datos en memoria

En una lista enlazada, cada nodo vive en el montón y los une un apuntador sig; el objeto lista solo guarda la cabeza (y su destructor recorre y libera cada nodo). Un nodo doble ocupa un apuntador más (ant). En una lista circular no hay nullptr al final: al liberar, detente al volver al primero.

lista (automática)
cabeza = 0x200
nodo · 0x200
3 | sig = 0x300
nodo · 0x300
8 | sig = nullptr

Un arreglo son cajas contiguas; salirse del rango pisa memoria ajena (comportamiento indefinido). vector y string son un objeto pequeño en el marco + sus datos en el montón (un string corto normalmente cabe dentro del propio objeto). size() es cuántos hay; capacity(), cuántos caben sin mudarse. Si push_back supera la capacidad, los datos se mudan y las direcciones e iteradores viejos dejan de valer. map/set también usan nodos en el montón.

10. RAII y apuntadores inteligentes

RAII: ata un recurso (memoria del montón, un archivo abierto…) a la vida de un objeto. El constructor lo toma y el destructor lo libera solo. Si se lanza una excepción, se destruyen los objetos automáticos de los marcos que se abandonan (desenrollado de la pila), así que lo suyo se libera; un new suelto, en cambio, se fuga.

{
    auto p = std::make_unique<Nodo>(5);   // dueño único
    std::ifstream f("datos.txt");         // dueño del archivo
}   // aquí: se cierra el archivo y se hace delete del Nodo, solos
TipoDueño
unique_ptruno solo; no se copia, se mueve; libera en su destructor
shared_ptrvarios; un contador en el montón; libera cuando muere el último
vector, string, stack, queue, listel contenedor: libera su montón al destruirse

11. Mover en vez de copiar

Copiar un vector duplica todos sus datos del montón. Mover los roba: el objeto nuevo se queda con el apuntador a esos datos y el viejo queda vacío. El viejo sigue siendo válido (puedes asignarle otra cosa), pero no cuentes con su contenido: para la biblioteca estándar queda en un estado «válido pero no especificado».

a (antes)
datos → 0x200
b = std::move(a)
datos → 0x200
a (después)
vacío
std::vector<int> b = std::move(a);   // no copia elementos: cambia de dueño

12. Hilos: qué se comparte y qué no

Cada hilo ejecuta sus propias funciones, así que en la práctica cada uno tiene su propia memoria automática (su propia pila de llamadas, con sus marcos y sus variables locales). Lo demás se comparte: el montón, la memoria estática (globales y static) y la zona de código. Por eso dos hilos pueden ver el mismo objeto a la vez.

hilo 1
sus locales
memoria automática propia
hilo 2
sus locales
memoria automática propia
compartido
montón · estática · código
lo ven todos los hilos

Si un hilo escribe en un dato mientras otro lo lee o lo escribe, sin mutex ni atomic, hay una carrera de datos, y eso es comportamiento indefinido. Las variables thread_local son la excepción: cada hilo tiene su propia copia.

int contador = 0;                    // estática: compartida por todos los hilos
std::mutex m;
void sumar() {
    int local = 0;                   // automática: cada hilo tiene la suya
    std::lock_guard<std::mutex> g(m);
    ++contador;                      // compartido: protegido por el mutex
}

13. La caché: por qué lo contiguo es rápido

El procesador no lee la memoria byte a byte: trae bloques (normalmente de 64 bytes) a una memoria pequeña y muy rápida, la caché. Si lo siguiente que usas está justo al lado, ya está en la caché y sale casi gratis. Si está lejos, hay que ir a buscarlo, y eso es mucho más lento.

De ahí la regla práctica: lo contiguo es rápido. Un vector guarda sus elementos uno tras otro; una lista enlazada tiene cada nodo en un sitio distinto del montón. Recorrer los dos es O(n), pero el vector suele ganar con mucha diferencia. Igual con una matriz: recorrerla en el orden en que está guardada (por filas) es más rápido que saltar por columnas.

vector
[1][2][3][4]…
contiguo: un bloque trae varios
lista
[1]→ … [2]→ … [3]
disperso: un viaje por nodo

La complejidad O grande no ve la caché: para saber cuál es más rápido de verdad, mide.

14. Herramientas para ver los errores

Los errores de memoria a menudo no fallan al momento: el programa «parece» funcionar. Estas herramientas los hacen visibles. C++ te da el control de la memoria; la ventaja es velocidad, el precio es que el cuidado es tuyo.

HerramientaQué detecta
g++ -g -fsanitize=addressAddressSanitizer: salirse de un arreglo, usar tras delete, doble liberación y, en Linux, fugas al terminar
valgrind ./progfugas y accesos inválidos, sin recompilar (si está instalado)
contador de objetos vivosun static int vivos: ++ en el constructor, -- en el destructor; al final debe valer 0
g++ -std=c++17 -Wall -g -fsanitize=address lista.cpp -o prog && ./prog
