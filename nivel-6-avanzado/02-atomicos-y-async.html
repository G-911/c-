Atómicos, condition_variable y async

Contar sin cerrojo, esperar sin gastar y pedir resultados para luego. ~40 minutos.

Al terminar podrás: contar con un std::atomic sin mutex, construir una cola donde un hilo produce y otro consume (con condition_variable), y repartir una suma en varias tareas con std::async, recogiendo cada resultado con su future.

Antes de empezar: repite sin mirar el quiz de la lección 6.1 (hilos y mutex). Recordar lo de ayer es lo que hace que se quede.

Por qué. En la 6.1 lo resolviste todo con thread y mutex. Funciona, pero se queda corto en tres situaciones muy comunes: un simple contador (el mutex es demasiado), un hilo que tiene que esperar a que otro le dé trabajo, y una tarea de la que solo quieres el resultado. Cada una tiene su herramienta. Hoy ves las tres y, sobre todo, cuándo usar cada una.

Compila como en la 6.1: g++ -std=c++20 -Wall -pthread. Nada de esta lección necesita C++23.

1. std::atomic: el contador sin cerrojo

Un atómico es una variable cuyas operaciones no se pueden partir: el «leer, sumar 1, escribir» de contador++ pasa en un solo paso indivisible. Ningún otro hilo puede colarse en medio.

#include <atomic>

atomic<int> contador = 0;     // el único cambio respecto a la carrera de la 6.1

void sumar() {
    for (int i = 0; i < 100000; i++)
        contador++;            // atómico: nadie se pisa
}
// main: dos hilos, join, cout ... → contador = 200000, siempre

Lo ejecutamos: 200000, y ThreadSanitizer no avisa de nada. Sin mutex, sin lock_guard.

EscribesHace (todo en un paso)
contador++, contador += 5suma
contador.load()lee el valor
contador.store(0)escribe un valor
contador.fetch_add(1)suma y devuelve el valor de antes

Error típico: creer que todo lo que toca un atómico es atómico.

atomic<int> contador = 0;
contador = contador + 1;     // ¡DOS pasos: un load y luego un store!

Cada paso es atómico, pero entre los dos se cuela el otro hilo. Lo ejecutamos con dos hilos de 100 000: salió 150538, 140873, 153417. Y lo peor: TSan no avisa, porque técnicamente no es una carrera de datos; es un error de lógica. Usa contador++ o contador += 1, que son una sola operación.

Límite: el atómico protege una variable. Si tienes que cambiar dos cosas juntas (el saldo de dos cuentas, una cola y su tamaño), necesitas un mutex: dos atómicos separados no hacen una operación atómica.

2. condition_variable: esperar dormido

El patrón más común con hilos es el productor-consumidor: un hilo produce datos y los mete en una cola; otro los saca y los procesa. Piensa en una cocina: el cocinero deja platos, el camarero los lleva.

¿Qué hace el camarero si no hay platos? La idea ingenua es preguntar sin parar:

while (cola.empty()) { }     // MAL: gasta un núcleo al 100 % y además es una carrera

La buena es dormir hasta que lo avisen. Eso es una condition_variable: un timbre que un hilo toca y otro espera.

#include <condition_variable>
#include <queue>

queue<int> cola;
mutex m;
condition_variable hayDatos;
bool terminado = false;

void productor() {
    for (int i = 1; i <= 3; i++) {
        { lock_guard<mutex> candado(m); cola.push(i); }   // meter, protegido
        hayDatos.notify_one();                              // tocar el timbre
    }
    { lock_guard<mutex> candado(m); terminado = true; }    // avisar del final
    hayDatos.notify_one();
}

void consumidor() {
    while (true) {
        unique_lock<mutex> candado(m);
        hayDatos.wait(candado, [] { return !cola.empty() || terminado; });
        if (cola.empty()) break;           // despertó porque terminó
        int x = cola.front(); cola.pop();
        candado.unlock();                  // soltar antes de trabajar
        cout << "consumí " << x << "\n";
    }
}

Con thread c(consumidor), p(productor); y sus join(), la salida real es consumí 1, consumí 2, consumí 3, y termina.

Lo importante está en wait(candado, condición):

  1. Si la condición ya se cumple, sigue sin dormir.
  2. Si no, abre el mutex y duerme (así el productor puede entrar a meter).
  3. Al despertar, vuelve a cerrar el mutex y comprueba otra vez la condición.

Por eso necesita unique_lock y no lock_guard: tiene que poder abrir y cerrar el mutex por dentro. Y por eso lleva la condición: un hilo puede despertarse sin que nadie lo avise (un «despertar espurio», según cppreference), y la condición hace que vuelva a dormirse.

Error típico: la condición sin la salida. Si el consumidor espera con [] { return !cola.empty(); } (sin || terminado), al acabarse los datos se duerme y nadie lo despierta nunca: el programa se queda colgado, como en un interbloqueo. Toda espera necesita una forma de terminar. Y avisa después de cambiar el dato, con notify_one() (despierta a uno) o notify_all() (a todos; úsalo al cerrar, para que salgan todos los consumidores).

3. std::async y std::future: pedir un resultado para luego

Muchas veces no quieres «un hilo»: quieres un resultado calculado en paralelo. async lanza la tarea y te da un future: un vale que canjeas más tarde con get().

#include <future>

long long sumarHasta(int n) {
    long long s = 0;
    for (int i = 1; i <= n; i++) s += i;
    return s;
}

future<long long> f = async(launch::async, sumarHasta, 1000);   // arranca ya
cout << "mientras tanto, main sigue...\n";
cout << "resultado = " << f.get() << "\n";   // espera si aún no acabó → 500500

Ventajas frente a thread:

  • Devuelve un valor. Con thread tendrías que escribirlo en una variable compartida.
  • Las excepciones viajan. Si la tarea lanza, la excepción salta en get(), en tu hilo, donde la puedes atrapar (lección 4.4).
  • No hay join que olvidar. get() ya espera.
int dividir(int a, int b) {
    if (b == 0) throw invalid_argument("entre cero");
    return a / b;
}

future<int> g = async(launch::async, dividir, 1, 0);
try {
    cout << g.get();
} catch (const invalid_argument& e) {
    cout << "error: " << e.what();      // salida real: error: entre cero
}

Tres trampas de async:

  • Pon launch::async. Sin él, la biblioteca puede decidir no crear hilo y ejecutar la tarea más tarde, dentro de get(): cero paralelismo.
  • Guarda el future. Si escribes async(launch::async, f); sin guardarlo, el future temporal se destruye en esa misma línea y su destructor espera a que f termine: el código queda secuencial (cppreference — async, Notes).
  • get() solo una vez. Después el future queda vacío (valid() es false) y llamarlo otra vez es comportamiento indefinido.

Regla de oro: cuanto menos compartan los hilos, mejor. Lo ideal es que cada tarea trabaje con sus propios datos y devuelva un resultado (async). Compartir con mutex es el plan B; los atómicos, para datos sueltos.

5. Una mención: el modelo de memoria

Debajo de todo esto hay una parte del estándar llamada modelo de memoria: las reglas de qué escritura de un hilo ve otro hilo, y cuándo. Los procesadores y los compiladores reordenan instrucciones para ir más rápido, y sin esas reglas un hilo podría ver los cambios de otro en un orden distinto al escrito.

No tienes que dominarlo ahora. Lo que necesitas saber: los atómicos aceptan un segundo argumento, el memory_order (relaxed, acquire, release...), para relajar esas garantías a cambio de velocidad. Por defecto usan la más estricta, seq_cst, que es la que se comporta «como esperas» (cppreference — memory_order). Quédate con el valor por defecto hasta que tengas una medición que diga lo contrario.

¿Qué pasa en la memoria?

Un atomic<int> no vive en ningún sitio especial: ocupa su caja donde lo declares (el contador global, en la memoria estática). Lo distinto es cómo se toca: el procesador hace la operación entera sin dejar entrar a otro núcleo. Para un int, en esta máquina contador.is_lock_free() da true: no hay ningún mutex escondido.

En tu ColaSegura, el objeto queue guarda sus datos en el montón (heap), y el montón es uno solo para todos los hilos: por eso va con mutex. La variable x de cada consumidor, en cambio, está en la memoria automática (la pila de llamadas o stack) de su hilo, y no hay que protegerla. Con async, el resultado no viaja por tu código: la tarea lo deja en un «estado compartido» entre ella y el future (normalmente en el montón), y get() lo recoge de allí.
