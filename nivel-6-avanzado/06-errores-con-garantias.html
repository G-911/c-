Errores con garantías

Lanzar una excepción no basta: hay que dejar las cosas en buen estado. ~40 minutos.

Al terminar podrás: decir qué garantía da una función cuando algo falla (básica, fuerte o nothrow), conseguir la fuerte con «copiar y luego intercambiar», explicar con un contador por qué vector copia en vez de mover si falta noexcept, y devolver errores sin excepciones con std::expected (C++23).

Antes de empezar: repite sin mirar el quiz de la lección 6.5 (biblioteca moderna). Recordar lo de ayer es lo que hace que se quede.

Por qué. En la lección 4.4 aprendiste a lanzar y atrapar. Pero quedó una frase suelta: «se comprueba antes de tocar nada; si lanzas a mitad de cambio, la pila queda rota». Hoy esa frase se convierte en una herramienta. Es lo que separa código que «casi siempre funciona» de código en el que puedes confiar, y es exactamente lo que la biblioteca estándar promete en cada función.

1. El problema: fallar a mitad de camino

Esta función cobra monto a cada saldo. Si alguno no alcanza, lanza:

void cobrar(vector<int>& saldos, int monto) {
    for (int& s : saldos) {
        if (s < monto) throw runtime_error("saldo insuficiente");
        s -= monto;
    }
}

vector<int> s = {10, 5, 8};
try { cobrar(s, 6); } catch (const runtime_error&) {}
// s queda en {4, 5, 8}

Al primero ya le cobró; al segundo no pudo; al tercero ni llegó. No hay fugas y el vector funciona, pero quien atrapa el error no sabe a quién se le cobró. Un banco no puede vivir con eso.

2. Las cuatro garantías

Ante una excepción, cada función promete uno de estos niveles (LearnCpp 27.9, cppreference):

GarantíaSi algo lanza...Ejemplo
sin garantíapuede haber fugas o objetos rotosun new suelto antes de algo que lanza (4.4)
básicano hay fugas y todo sigue siendo válido, pero puede haber cambiadocobrar de arriba
fuertetodo queda exactamente como antes de la llamada: o sale entera o no pasó nadavector::push_back; el pop de la 4.4
nothrownunca lanzadestructores, swap, mover

La básica es el mínimo exigible a cualquier función. La fuerte es la que quieres en las operaciones importantes. Y la nothrow es la pieza que hace posible la fuerte, como verás ahora.

3. Cómo conseguir la garantía fuerte

La receta tiene dos pasos: haz el trabajo en una copia (si algo falla, el original ni se entera) y confírmalo con algo que no puede fallar.

void cobrarFuerte(vector<int>& saldos, int monto) {
    vector<int> copia = saldos;          // 1. trabajar en una copia
    for (int& s : copia) {
        if (s < monto) throw runtime_error("saldo insuficiente");
        s -= monto;
    }
    saldos.swap(copia);                  // 2. confirmar: swap no lanza
}
// con {10, 5, 8} y 6: lanza y s sigue en {10, 5, 8}

Si lanza en el bucle, lo que se pierde es la copia. Si llega al final, el swap solo intercambia los apuntadores internos de los dos vectores: no copia elementos y no puede fallar. Cuando se pueda, hay una forma aún más barata: comprobar todo antes de tocar nada, como el pop de la 4.4.

Error típico: el paso de confirmar puede fallar. Si en lugar de swap escribes saldos = copia;, eso copia otra vez los elementos y puede lanzar (por ejemplo, si se acaba la memoria): la garantía fuerte se pierde en la última línea. El paso final tiene que ser nothrow: swap o un movimiento noexcept.

4. noexcept: la promesa de no lanzar

noexcept (C++11) en una función le dice al compilador y a quien la llama: «esta función no lanza». Desde C++17 forma parte del tipo de la función.

void f() noexcept {}         // promete no lanzar
void g() {}                  // sin promesa

cout << noexcept(f()) << noexcept(g());   // 10: el operador noexcept pregunta (sin ejecutar)

¿Y si una función noexcept lanza de todos modos? No se atrapa: el programa llama a std::terminate() y se corta. g++ te avisa si lo ve venir:

void f() noexcept { throw runtime_error("x"); }
// warning: ‘throw’ will always call ‘terminate’ [-Wterminate]
// al ejecutar: terminate called after throwing an instance of 'std::runtime_error'

¿Qué marcar con noexcept? Lo que de verdad no puede fallar: el constructor y la asignación de movimiento, swap e intercambiar. Los destructores ya lo son por defecto. No lo pongas «por si acaso» en funciones que hacen new o llaman a cosas que lanzan: quitarlo luego rompe a quien confiaba en la promesa (LearnCpp 27.9).

5. Por qué a vector le importa tanto (comprobado)

En la lección 4.7 leíste que vector solo mueve al crecer si el movimiento es noexcept. Vamos a verlo con un contador. Dos tipos iguales; solo cambia la palabra noexcept:

int copias = 0, movimientos = 0;

struct ConNoexcept {
    ConNoexcept() {}
    ConNoexcept(const ConNoexcept&) { copias++; }
    ConNoexcept(ConNoexcept&&) noexcept { movimientos++; }   // promete no lanzar
};

struct SinNoexcept {
    SinNoexcept() {}
    SinNoexcept(const SinNoexcept&) { copias++; }
    SinNoexcept(SinNoexcept&&) { movimientos++; }            // sin promesa
};

template <typename T>
void probar(const char* nombre) {
    copias = movimientos = 0;
    vector<T> v;
    for (int i = 0; i < 5; i++) v.push_back(T{});   // cada T{} entra moviéndose
    cout << nombre << ": " << copias << " copias, " << movimientos << " movimientos\n";
}

int main() {
    probar<ConNoexcept>("con noexcept");
    probar<SinNoexcept>("sin noexcept");
}

Salida real (g++ 15, igual con -std=c++17 y -std=c++23):

con noexcept: 0 copias, 12 movimientos
sin noexcept: 7 copias, 5 movimientos

Las cuentas: los 5 T{} entran moviéndose (5). Al crecer, g++ duplica la capacidad (1 → 2 → 4 → 8), así que muda los elementos viejos tres veces: 1 + 2 + 4 = 7. Con noexcept esos 7 se mueven; sin él, se copian. Con una Pila de mil nodos, cada una de esas copias son mil new.

¿Por qué? Porque push_back promete la garantía fuerte (cppreference). Imagina que muda 5 elementos y el 3.º falla:

  • Copiando, los originales siguen intactos: tira el bloque nuevo y el vector queda como estaba. Garantía fuerte.
  • Moviendo, el 1.º y el 2.º ya fueron «robados»: el bloque viejo está medio vacío. Devolverlos sería mover otra vez, y eso también podría fallar. No hay forma segura de deshacer.

Así que vector pregunta: «¿tu movimiento promete no lanzar?». Si sí, mueve. Si no, copia para ir a lo seguro. Esa pregunta tiene nombre: std::move_if_noexcept (LearnCpp 27.10). Una excepción: si el tipo no se puede copiar (como unique_ptr), mueve igualmente y la garantía fuerte se pierde si ese movimiento lanza.

6. Copy-and-swap: un operator= con garantía fuerte

Vuelve al operator= de la lección 3.5: comprobar a = a, vaciar() los nodos viejos y copiar los de otra con new. Si un new falla a mitad de la copia, tu lista ya perdió sus nodos y tiene solo parte de los nuevos. Garantía básica, como mucho.

El idioma copy-and-swap (copiar e intercambiar) le da la vuelta. Para la Pila de la 4.7 (con tope y n):

void intercambiar(Pila& otra) noexcept {
    swap(tope, otra.tope);   // solo intercambia dos apuntadores...
    swap(n, otra.n);         // ...y dos int: no puede fallar
}

Pila& operator=(Pila otra) noexcept {   // por VALOR: al entrar, otra ya es la copia
    intercambiar(otra);                 // me quedo los nodos nuevos; otra, los viejos
    return *this;
}                                       // otra muere aquí y libera los nodos VIEJOS

Tres ventajas de golpe (cppreference, «copy-and-swap idiom»):

  1. Garantía fuerte. Lo que puede fallar (copiar) ocurre al pasar el parámetro, antes de entrar. Si falla, *this ni se ha tocado.
  2. a = a funciona sin if. Se copia a, se intercambia y se libera lo viejo: el resultado es igual.
  3. Sirve también para mover. Con a = std::move(b); el parámetro se construye moviendo (sin copiar nodos). Un solo operator= hace de los dos.

El precio: siempre crea nodos nuevos, aunque a ya tuviera sitio para reutilizar. Para una lista enlazada da igual; para un vector grande, a veces importa.

Error típico: dejar también el operator=(Pila&&) de la 4.7. Con los dos, a = std::move(b); encaja igual de bien en ambos y g++ no sabe cuál elegir:

error: ambiguous overload for ‘operator=’

Con copy-and-swap, el operator= por valor sustituye a los dos de antes (copia y movimiento). Los constructores de copia y de movimiento sí se quedan: son los que fabrican el parámetro.

7. std::expected: el error como valor (C++23)

A veces el error no es excepcional: un dato mal escrito por el usuario, un archivo que falta. expected<T, E> (C++23, <expected>) guarda o un resultado de tipo T, o un error de tipo E. Es como el optional de la 6.5, pero cuando no hay valor te dice por qué.

#include <expected>

expected<int, string> dividir(int a, int b) {
    if (b == 0) return unexpected("división entre cero");   // el error
    return a / b;                                            // el valor
}

auto r = dividir(7, 2);
if (r) cout << *r;               // 3
auto e = dividir(1, 0);
if (!e) cout << e.error();       // división entre cero
cout << e.value_or(-1);          // -1

Igual que en optional: *r sin comprobar es comportamiento indefinido; r.value() lanza (bad_expected_access) si hay error. El error no se puede ignorar sin querer: para llegar al int tienes que mirar. Y se pasa hacia arriba a mano:

expected<int, string> media(const vector<int>& v) {
    int suma = 0;
    for (int x : v) suma += x;
    auto r = dividir(suma, (int)v.size());
    if (!r) return unexpected(r.error());   // pasar el error a quien me llamó
    return *r;
}
// media({4, 6}) → 5      media({}) → error "división entre cero"

C++23 trae también and_then y transform para encadenar pasos sin tantos if; con lo de arriba te basta para empezar.

¿Qué pasa en la memoria?

En a = b; con copy-and-swap, el parámetro otra nace en el marco de operator= (memoria automática o stack) y sus nodos nuevos, en el montón (heap). Durante un instante conviven los nodos viejos y los nuevos: es el precio de la garantía fuerte. El intercambio no mueve ni un nodo; solo cambia quién es el dueño de cada cadena:

a (en main)
tope →
nodos nuevos
otra (marco de operator=)
tope →
nodos viejos de a
al salir de operator=
~Pila()
libera los viejos

Es RAII haciendo de «deshacer»: si la copia falla, el destructor de lo ya construido limpia; si sale bien, el de otra se lleva lo viejo. Un detalle: si un constructor lanza a medias, su propio destructor no se ejecuta (el objeto nunca terminó de nacer). Por eso el constructor de copia del miniproyecto libera en su catch lo que ya había pedido.

Miniproyecto 6.6 · Un vector que no se rompe

Abre ejercicios/06-errores-con-garantias.cpp. Trae una Pieza que cuenta sus copias (y que las pruebas pueden hacer fallar a propósito) y un VectorPiezas a medio hacer. Completa:

  1. noexcept en el constructor y la asignación de movimiento de Pieza.
  2. crecer() con garantía fuerte: bloque nuevo, pasar con move_if_noexcept, y si algo lanza, liberar lo nuevo y relanzar.
  3. push_back con garantía fuerte. El orden importa: la prueba w.push_back(w[0]) con el vector lleno falla si creces antes de copiar (lees un elemento del bloque que acabas de liberar).
  4. intercambiar y el operator= por copy-and-swap.
  5. dividir con expected y describir, que lo usa.

Compílalo desde la carpeta ejercicios (C++23 por <expected>):

g++ -std=c++23 -Wall -pthread 06-errores-con-garantias.cpp -o prog && ./prog

Al principio verás casi todo en ✗. Terminaste cuando salgan todas en ✓. Unos 20 minutos. Si quieres ver el error del orden de push_back con tus propios ojos, compílalo mal a propósito con -fsanitize=address -g: avisa de heap-use-after-free.

Si te atascas: push_back son cuatro líneas: Pieza copia = x;, if (n == cap) crecer();, datos[n] = std::move(copia); y n++;. El operator= son dos: intercambiar(otro); y return *this;. Si la prueba de las «5 copias» falla, revisa el paso 1. La solución está en soluciones/06-errores-con-garantias.cpp; ábrela solo después de intentarlo de verdad.
