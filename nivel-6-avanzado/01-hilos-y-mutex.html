Hilos y mutex

Hacer varias cosas a la vez sin que se pisen. ~40 minutos.

Al terminar podrás: lanzar varios hilos con std::thread, esperarlos con join(), proteger un contador compartido con un std::mutex para que el resultado sea exacto, y bloquear dos cuentas con scoped_lock sin que el programa se quede congelado.

Antes de empezar: repite sin mirar el quiz de la lección 5.7 (grafos). Recordar lo de ayer es lo que hace que se quede.

Por qué. Bienvenido al Nivel 6. Hasta ahora, todos tus programas hacían una sola cosa a la vez: una línea, luego la siguiente. Eso es un solo hilo. Tu procesador, en cambio, tiene varios núcleos (el ordenador donde se probó esta lección puede correr 20 hilos a la vez) y casi todos están parados mientras tu programa corre. Usarlos es lo que hacen los videojuegos, los navegadores y los servidores. En la lección 4.8 lo mencionamos de pasada; hoy lo haces de verdad, y ves su peligro principal.

1. Un hilo es un «main» extra

Un hilo (thread) es una línea de ejecución. Tu programa empieza con uno, el de main. Con std::thread arrancas otros que corren a la vez, cada uno con su propia función.

#include <thread>

void saludar() { cout << "hola desde otro hilo\n"; }

int main() {
    thread t(saludar);   // saludar() empieza YA, en paralelo con main
    cout << "main sigue\n";
    t.join();            // main espera aquí a que t termine
}

join() significa «espera a que ese hilo acabe». El orden de las dos líneas impresas no está garantizado: depende de quién llegue antes.

Desde ahora compilarás con dos cambios:

g++ -std=c++20 -Wall -pthread programa.cpp -o prog && ./prog
  • -pthread: enlaza el soporte de hilos del sistema.
  • -std=c++20: solo porque más abajo usamos jthread, que es de C++20. Todo lo demás de la lección existe desde C++11/17.

Pasar argumentos

Los argumentos van detrás de la función. Ojo: el hilo los copia. Si la función recibe una referencia, tienes que decirlo con ref():

void duplicar(int& x) { x *= 2; }

int n = 5;
thread t(duplicar, ref(n));   // sin ref(): NO compila
t.join();
cout << n;                    // 10

Con una lambda (lección 4.3) es más cómodo, y es lo que verás casi siempre:

thread t([&] { n *= 2; });   // captura n por referencia

Error típico: olvidar el join(). Si un thread se destruye mientras su hilo sigue «unido» (sin join()), C++ llama a std::terminate() y el programa se corta (cppreference — ~thread):

int main() {
    thread t(saludar);
}   // t se destruye sin join → "terminate called without an active exception"

Lo ejecutamos: el programa aborta. La solución moderna es la del punto siguiente.

jthread: el hilo que se espera solo (C++20)

std::jthread es igual que thread, pero su destructor hace el join() por ti (cppreference). Es RAII, como en la lección 4.5: el recurso se suelta en el destructor.

{
    jthread j([] { cout << "hola\n"; });
}   // aquí el destructor espera a que j termine: nada se corta

2. La carrera de datos: el peligro de verdad

Dos hilos suman 100 000 cada uno a la misma variable. Debería dar 200 000.

int contador = 0;                 // compartido por los dos hilos

void sumar() {
    for (int i = 0; i < 100000; i++)
        contador++;               // leer, sumar 1, escribir: tres pasos
}

int main() {
    thread a(sumar);
    thread b(sumar);
    a.join();
    b.join();
    cout << "contador = " << contador << " (esperado 200000)\n";
}

Lo compilamos con g++ -std=c++23 -Wall -pthread y lo ejecutamos cinco veces seguidas en esta máquina. Salida real:

contador = 162155 (esperado 200000)
contador = 116116 (esperado 200000)
contador = 188537 (esperado 200000)
contador = 128954 (esperado 200000)
contador = 100000 (esperado 200000)

Cinco ejecuciones, cinco resultados, todos mal. ¿Por qué? Porque contador++ no es un paso: son tres.

Hilo AHilo Bcontador
lee 4141
lee 4141
escribe 4242
escribe 4242 ← se perdió una suma

Eso es una carrera de datos (data race): dos hilos tocan la misma variable a la vez, al menos uno escribe, y nada los ordena. El estándar dice que entonces el comportamiento es indefinido (cppreference — data races): no «da un número raro», sino que puede pasar cualquier cosa.

«En mi máquina funciona» no prueba nada. Con optimización (-O2) el mismo programa dio 200000 las cinco veces: el compilador convirtió el bucle entero en una sola instrucción (contador += 100000) y la carrera casi nunca se nota. Sigue siendo comportamiento indefinido. Mañana, con otro compilador o con más hilos, falla. Por eso hacen falta herramientas que la detecten, no ojos.

El detector: -fsanitize=thread

Igual que -fsanitize=address caza errores de memoria, ThreadSanitizer (TSan) caza carreras de datos mientras el programa corre:

g++ -std=c++20 -pthread -fsanitize=thread -g carrera.cpp -o prog && ./prog

Salida real (recortada):

WARNING: ThreadSanitizer: data race
  Read of size 4 at 0x... by thread T2:
    #0 sumar() carrera.cpp:9
  Previous write of size 4 at 0x... by thread T1:
    #0 sumar() carrera.cpp:9
  Location is global 'contador' of size 4
SUMMARY: ThreadSanitizer: data race carrera.cpp:9 in sumar()

Te dice qué variable (contador), qué línea (la 9) y qué hilos. Y lo avisa aunque el número salga bien por casualidad. Dos detalles: no se puede combinar con -fsanitize=address en la misma compilación (g++ lo rechaza), y el programa corre más lento mientras vigila.

3. std::mutex: de uno en uno

Un mutex (de mutual exclusion, exclusión mutua) es un cerrojo. Solo un hilo puede tenerlo a la vez; los demás esperan en la puerta. El trozo de código protegido se llama sección crítica.

#include <mutex>

int contador = 0;
mutex m;                               // un cerrojo para contador

void sumar() {
    for (int i = 0; i < 100000; i++) {
        lock_guard<mutex> candado(m);  // cierra m (o espera a que se abra)
        contador++;                    // sección crítica: un hilo a la vez
    }                                  // candado se destruye → abre m
}

Ahora sale contador = 200000 siempre, y TSan no dice nada.

lock_guard es RAII otra vez: cierra en el constructor, abre en el destructor. Existen m.lock() y m.unlock(), pero si entre los dos hay un return o una excepción, el unlock no llega y los demás hilos esperan para siempre. Con lock_guard eso no pasa.

Mejor aún: no compartir. El mutex hace que los hilos hagan cola, y la cola cuesta. Si cada hilo suma en su propia variable y al final juntas los resultados, no hay nada que proteger. Es la idea de contarPares en el miniproyecto: cada hilo escribe en su casilla de un vector.

4. Interbloqueo: dos hilos que se esperan para siempre

Ahora con dinero. Cada cuenta tiene su propio mutex. Para transferir hay que bloquear las dos:

struct Cuenta { int saldo = 1000; mutex m; };

void transferir(Cuenta& de, Cuenta& a, int monto) {
    lock_guard<mutex> l1(de.m);     // 1.º bloquea la de origen
    lock_guard<mutex> l2(a.m);      // 2.º bloquea la de destino
    de.saldo -= monto;
    a.saldo += monto;
}

// hilo 1: transferir(ana, beto, 1) cien mil veces
// hilo 2: transferir(beto, ana, 1) cien mil veces

Lo ejecutamos tres veces con un límite de 5 segundos (timeout 5 ./prog). Las tres veces se quedó congelado hasta que lo mataron. ¿Qué pasó?

Hilo 1: ana → betoHilo 2: beto → ana
cierra ana.mcierra beto.m
espera beto.m… (la tiene el 2)espera ana.m… (la tiene el 1)
ninguno suelta lo suyo: esperan para siempre

Eso es un interbloqueo (deadlock). El programa no se cae: se queda quieto, sin error, sin mensaje. Es de los fallos más difíciles de encontrar.

La solución: scoped_lock con los dos a la vez

void transferir(Cuenta& de, Cuenta& a, int monto) {
    scoped_lock candado(de.m, a.m);  // bloquea las DOS sin interbloqueo
    de.saldo -= monto;
    a.saldo += monto;
}

scoped_lock (C++17) recibe varios mutex y usa un algoritmo que evita el interbloqueo (cppreference). Con este cambio, las tres ejecuciones terminaron al instante con total = 2000.

Reglas para no interbloquearte:

  • Si necesitas varios mutex, ciérralos juntos con scoped_lock.
  • Si no puedes, ciérralos siempre en el mismo orden en todo el programa.
  • No llames a funciones desconocidas con un mutex cerrado: pueden querer el mismo.
  • Mantén la sección crítica corta: entra, toca el dato, sal.

5. ¿Cuántos hilos lanzo?

unsigned n = thread::hardware_concurrency();   // en esta máquina: 20

Devuelve cuántos hilos puede correr el hardware a la vez. Es solo una pista, y si no lo sabe devuelve 0 (cppreference): compruébalo siempre. Lanzar 1000 hilos en 20 núcleos no va 50 veces más rápido: los hilos se turnan y el turno cuesta. Para trabajo de cálculo, una cantidad cercana a ese número es un buen punto de partida.

¿Qué pasa en la memoria?

Cada hilo tiene su propia memoria automática (su propia pila de llamadas o stack, con sus marcos). Por eso el i del bucle de sumar() no da problemas: hay un i distinto en cada hilo. En cambio, la memoria estática y el montón (heap) son uno solo para todos. contador es global, vive en la estática, y los dos hilos escriben en la misma caja: de ahí la carrera.

pila del hilo A
marco de sumar: i
solo suyo
pila del hilo B
marco de sumar: i
solo suyo
estática (compartida)
contador, m
la ven los dos: protégela

Cuidado con [&]: en sumarConHilos del miniproyecto, el hilo usa contador y m, que viven en el marco de esa función. Si la función terminara antes del join(), los hilos seguirían escribiendo en un marco ya liberado. El join() antes del return no es cortesía: alarga el tiempo de vida lo necesario.

Miniproyecto 6.1 · Hilos que no se pisan

Abre ejercicios/01-hilos-y-mutex.cpp. Completa las cuatro funciones:

  1. sumarConHilos(nHilos, porHilo): lanza nHilos hilos que suman 1 a un contador compartido, protegido con mutex. El resultado debe ser exacto.
  2. contarPares(v, nHilos): reparte el vector en trozos, un hilo por trozo, cada uno cuenta en su casilla. Sin mutex.
  3. transferir(de, a, monto): con scoped_lock; si no hay saldo, devuelve false sin tocar nada. Una prueba lanza cuatro hilos transfiriendo en los dos sentidos: si te interbloqueas, lo detecta a los 10 segundos y te avisa.
  4. hilosParaUsar(): hardware_concurrency(), o 2 si devuelve 0.

Compílalo desde la carpeta ejercicios:

g++ -std=c++20 -Wall -pthread 01-hilos-y-mutex.cpp -o prog && ./prog

Cuando salga todo en ✓, pásale el detector:

g++ -std=c++20 -Wall -pthread -fsanitize=thread -g 01-hilos-y-mutex.cpp -o prog && ./prog

Si no aparece ningún WARNING: ThreadSanitizer, terminaste. Unos 20 minutos.

Si te atascas: el esqueleto de sumarConHilos es vector<thread> hilos;, un bucle con hilos.push_back(thread([&] { ... })); y otro bucle con h.join(). En contarPares, captura i, desde y hasta por copia: si los capturas por referencia, el bucle de fuera los cambia mientras el hilo los usa. La solución está en soluciones/01-hilos-y-mutex.cpp; ábrela solo después de intentarlo de verdad.
