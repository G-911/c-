Diseño

Código que se puede cambiar sin romperlo todo: dos principios y seis recetas. ~35 minutos.

Al terminar podrás: separar un programa en piezas que cambian por separado, y reconocer y escribir cuatro patrones (estrategia, fábrica, observador y RAII) y tres técnicas de C++ (PIMPL, CRTP y type erasure), cada una en su versión mínima.

Antes de empezar: repite sin mirar el quiz de la lección 6.6 (errores con garantías). Recordar lo de ayer es lo que hace que se quede.

Por qué. Hasta ahora cada lección enseñaba una herramienta. Esta enseña a ordenarlas. Un programa de 100 líneas aguanta cualquier desorden; uno de 10 000, no. En la universidad lo verás como «patrones de diseño», y en cualquier proyecto real lo necesitarás el día que alguien diga «¿y si además...?». La idea de fondo es una sola: lo que cambia por separado, se escribe por separado.

Todo el código de esta lección es C++17. Se compila con g++ -std=c++17 -Wall -pthread archivo.cpp -o prog.

1. Dos principios

Responsabilidad única

Una clase, un motivo para cambiar. Si tu Carrito suma precios, calcula descuentos, guarda en un archivo e imprime un ticket, cualquier cambio en cualquiera de esas cuatro cosas toca el Carrito. Mejor cuatro piezas pequeñas que se usan entre sí. Pregunta útil: ¿puedo describir lo que hace la clase sin decir «y»?

Composición antes que herencia

Herencia dice «es un». Composición dice «tiene un» (LearnCpp 23.2). Cuando dudes, elige composición: hereda solo si de verdad quieres todo lo de la base.

class PilaMala : public vector<int> {};   // herencia: hereda TODO lo de vector

class Pila {                              // composición: TIENE un vector
    vector<int> datos;
public:
    void push(int x) { datos.push_back(x); }
    void pop() { datos.pop_back(); }
    int top() const { return datos.back(); }
    bool vacia() const { return datos.empty(); }
};

PilaMala m;
m.push_back(1);
m.push_back(2);
m.insert(m.begin(), 99);   // ¡se coló por debajo! Ya no es una pila
cout << m.front();          // 99
// Con Pila, p.insert(...) ni compila: solo deja hacer lo de una pila

Con herencia, PilaMala no puede prometer nada: cualquiera la usa como vector. Con composición, tú decides qué se puede hacer.

2. Estrategia: cambiar el algoritmo sin tocar la clase

Un patrón de diseño es una solución con nombre a un problema que aparece una y otra vez. Este es el primero. El problema:

double Carrito::total() const {
    if (tipoDescuento == "ninguno") return subtotal();
    else if (tipoDescuento == "porcentaje") return subtotal() * (1 - valor / 100);
    else if (tipoDescuento == "navidad") ...   // y cada descuento nuevo, otro else if aquí
}

Cada descuento nuevo obliga a abrir el Carrito. La estrategia saca el algoritmo a su propia clase, detrás de una interfaz (la clase abstracta de la lección 2.6):

class Descuento {                                   // la interfaz: una sola cosa que hacer
public:
    virtual ~Descuento() = default;
    virtual double aplicar(double subtotal) const = 0;
};

class SinDescuento : public Descuento {
public:
    double aplicar(double s) const override { return s; }
};

class Porcentaje : public Descuento {
    double porcentaje;
public:
    explicit Porcentaje(double p) : porcentaje(p) {}
    double aplicar(double s) const override { return s * (1 - porcentaje / 100); }
};

// El Carrito guarda UNA estrategia y la usa, sin saber cuál es:
double Carrito::total() const { return descuento->aplicar(subtotal()); }

Ahora un descuento nuevo es una clase nueva. El Carrito no se toca. Y se puede cambiar en plena ejecución: c.cambiarDescuento(make_unique<Porcentaje>(10));.

3. Fábrica: crear sin nombrar la clase

¿Y si el tipo de descuento llega como texto, desde un archivo o desde el teclado? Alguien tiene que convertir "porcentaje" en un Porcentaje. Esa es la fábrica: una función que decide qué clase crear y la devuelve por la interfaz.

unique_ptr<Figura> crearFigura(const string& tipo, double medida) {
    if (tipo == "cuadrado") return make_unique<Cuadrado>(medida);
    if (tipo == "circulo")  return make_unique<Circulo>(medida);
    return nullptr;                       // no sé crear eso: que decida quien llama
}

auto f = crearFigura("cuadrado", 3);    // quien llama no nombra la clase concreta
if (f) cout << f->area();               // 9

El if por tipo no desaparece, pero queda en un solo sitio. Y la fábrica devuelve un unique_ptr: deja claro que quien la llama pasa a ser el dueño.

4. Observador: avisar a quien le interese

Cuando cambia el total del carrito, quizá la pantalla quiera redibujarse, y quizá un registro quiera anotarlo. El Carrito no debería conocerlos a todos. Con el observador, cada interesado se apunta, y el carrito avisa a la lista:

vector<function<void(double)>> observadores;   // la lista de interesados

void alCambiar(function<void(double)> f) { observadores.push_back(f); }

void avisar(double total) {
    for (auto& f : observadores) f(total);       // llama a cada uno
}

// Quien usa el carrito:
c.alCambiar([](double t) { cout << "nuevo total: " << t << "\n"; });

Los interesados son lambdas (lección 4.3) guardadas en std::function. Así se apunta cualquier cosa que se pueda llamar. Por qué eso funciona lo verás en la sección 8.

Error típico: un observador que captura por referencia algo que ya murió. Si la lambda captura [&] una variable local y el carrito la llama cuando esa variable ya no existe, es un apuntador colgante disfrazado. El observador debe vivir menos que lo que captura, o capturar por copia.

5. RAII también es un patrón

Ya lo conoces de la lección 4.5: el constructor toma un recurso y el destructor lo suelta. Sirve para cualquier «antes y después», no solo para memoria:

class Aviso {                          // RAII: el destructor hace el «después»
    string que;
public:
    Aviso(string q) : que(q) { cout << "empieza " << que << "\n"; }
    ~Aviso() { cout << "termina " << que << "\n"; }
};

void tarea() {
    Aviso a("tarea");
    cout << "trabajando...\n";
    throw 1;                           // aun así, el destructor se llama
}
// main: try { tarea(); } catch (int) { cout << "error atrapado\n"; }
// Muestra: empieza tarea / trabajando... / termina tarea / error atrapado

Así se hacen lock_guard (lección 6.1), los archivos que se cierran solos y los cronómetros que miden un bloque.

6. PIMPL: esconder el interior

Un .h con los atributos privados tiene un problema: si cambias un atributo privado, todos los .cpp que incluyen ese .h se recompilan (lección 4.6). En un proyecto grande, son minutos. PIMPL (pointer to implementation, «apuntador a la implementación») deja en el .h solo un apuntador:

// carrito.h — lo que ven los demás
class Carrito {
public:
    Carrito();
    ~Carrito();                     // declarado aquí, definido en el .cpp
    void agregar(const std::string& producto, double precio);
    double total() const;
private:
    struct Impl;                    // declarada, NO definida: una caja cerrada
    std::unique_ptr<Impl> impl;     // lo único que guarda el Carrito
};

// carrito.cpp — lo único que sabe qué hay dentro
struct Carrito::Impl {
    vector<pair<string, double>> productos;
    unique_ptr<Descuento> descuento = make_unique<SinDescuento>();
};
Carrito::Carrito() : impl(make_unique<Impl>()) {}
Carrito::~Carrito() = default;      // aquí Impl ya está completa

Ahora puedes añadir, quitar o cambiar lo que hay en Impl y solo se recompila carrito.cpp. A cambio, cada acceso pasa por un apuntador (cppreference — PImpl).

Error típico: escribir ~Carrito() = default; en el .h. El destructor de unique_ptr necesita saber cómo es Impl para borrarlo, y en el .h no lo sabe. g++ 15 da:

error: invalid application of ‘sizeof’ to incomplete type ‘Carrito::Impl’

Arreglo: en el .h solo ~Carrito();, y el = default en el .cpp, después de definir Impl. Lo mismo para el movimiento.

7. CRTP: polimorfismo en compilación

El virtual decide al ejecutar qué función llamar. A veces ya sabes el tipo al compilar y no quieres pagar ese salto. El CRTP (Curiously Recurring Template Pattern) es una clase que se pasa a sí misma a su base plantilla:

template <typename Derivada>
class Saludador {
public:
    void saludar() const {
        // sabe, al compilar, cuál es la clase hija: no hace falta virtual
        const Derivada& yo = static_cast<const Derivada&>(*this);
        cout << "Hola, soy " << yo.nombre() << "\n";
    }
};

class Perro : public Saludador<Perro> {     // se pasa a sí misma
public:
    string nombre() const { return "un perro"; }
};

Perro p;
p.saludar();     // Hola, soy un perro

La base da el código común (saludar) y la hija pone lo concreto (nombre). El precio: Saludador<Perro> y Saludador<Robot> son tipos distintos, así que no puedes meter un perro y un robot en el mismo vector. Para eso sigue haciendo falta virtual (cppreference — CRTP).

8. Type erasure: lo que hace std::function por dentro

std::function<int(int)> guarda una función normal, una lambda o un objeto con operator(). Son tres tipos sin nada en común, y aun así caben en el mismo vector:

int doble(int x) { return 2 * x; }
struct Sumador { int cuanto; int operator()(int x) const { return x + cuanto; } };

vector<function<int(int)>> ops;
ops.push_back(doble);
ops.push_back(Sumador{10});
ops.push_back([](int x) { return x * x; });
for (auto& f : ops) cout << f(3) << " ";    // 6 13 9

El truco se llama borrado de tipo (type erasure): por fuera, un solo tipo; por dentro, una interfaz virtual escondida y una plantilla que envuelve lo que sea. Esta es la versión mínima, hecha a mano:

class Dibujable {
    struct Concepto {                              // la interfaz, escondida
        virtual ~Concepto() = default;
        virtual void dibujar() const = 0;
    };
    template <typename T>
    struct Modelo : Concepto {                     // envuelve a CUALQUIER T con dibujar()
        T objeto;
        Modelo(T o) : objeto(std::move(o)) {}
        void dibujar() const override { objeto.dibujar(); }
    };
    unique_ptr<Concepto> caja;
public:
    template <typename T>
    Dibujable(T o) : caja(make_unique<Modelo<T>>(std::move(o))) {}
    void dibujar() const { caja->dibujar(); }
};

struct Circulo  { void dibujar() const { cout << "( )\n"; } };   // sin herencia
struct Cuadrado { void dibujar() const { cout << "[ ]\n"; } };   // sin herencia

vector<Dibujable> escena;
escena.push_back(Circulo{});
escena.push_back(Cuadrado{});
for (const auto& d : escena) d.dibujar();      // ( )  y luego  [ ]

Lo bueno: Circulo y Cuadrado no heredan de nada. Basta con que tengan dibujar(). Es el polimorfismo de la lección 2.6, pero sin obligar a nadie a heredar.

Error típico: patrones por todas partes. Un patrón resuelve un problema que tienes. Una fábrica para una sola clase, o una estrategia con un solo algoritmo, es código de más que alguien tendrá que leer. Empieza simple y saca el patrón cuando aparezca el segundo caso.

¿Qué pasa en la memoria?

Con PIMPL, el objeto Carrito que vive en el marco de main es solo un apuntador: sizeof(Carrito) da lo mismo que sizeof(unique_ptr<int>), normalmente 8 bytes. Todo lo demás (el vector de productos, el descuento, los observadores) está en un Impl en el montón (heap), y su dueño es ese unique_ptr.

marco de main
c.impl →
el Carrito: un apuntador
montón
Impl
productos, descuento, observadores
montón
Porcentaje
la estrategia, otro bloque

Por eso mover un Carrito es barato: se pasa el apuntador y el Impl no se mueve de sitio. El type erasure casi siempre usa el montón: cada Modelo<T> de Dibujable es un bloque aparte. std::function guarda dentro de sí un apuntador a función, sin pedir memoria; un objeto grande puede ir al montón (cppreference). El CRTP, en cambio, no añade nada en ejecución: todo se decide al compilar.
