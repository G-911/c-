Comportamiento indefinido y rendimiento

Por qué un programa con un error puede «funcionar» hasta que activas -O2, y por qué recorrer la memoria en orden es mucho más rápido. ~40 minutos.

Al terminar podrás: reconocer los comportamientos indefinidos más comunes, cazarlos con -fsanitize=undefined,address, y medir con <chrono> sin engañarte: con -O2, repitiendo, y entendiendo qué pinta la caché.

Antes de empezar: repite sin mirar el quiz de la lección 6.7 (diseño). Recordar lo de ayer es lo que hace que se quede.

Por qué. C++ es rápido porque confía en ti: no comprueba cada índice ni cada suma. El precio es el comportamiento indefinido: si rompes una regla, el programa puede hacer cualquier cosa, y el optimizador lo empeora. Las dos mitades de esta lección son las dos caras de esa confianza: no romper las reglas, y aprovechar la velocidad de verdad.

Todo el código de esta lección es C++17. Las salidas son reales: g++ 15.2 en esta máquina.

1. Qué es el comportamiento indefinido

El estándar de C++ dice qué hace cada operación correcta. Para algunas operaciones incorrectas dice algo más raro: «el comportamiento es indefinido» (undefined behavior, UB). No significa «da error» ni «da un valor raro». Significa que el estándar no promete nada: puede caerse, dar basura, o parecer que funciona (cppreference — Undefined behavior).

Ya te has cruzado con varios:

Ojo con el primero: con signo. Los unsigned no desbordan: dan la vuelta de forma definida (UINT_MAX + 1 es 0). Los int, no (LearnCpp 4.4).

2. Por qué el compilador lo aprovecha

La regla clave: el compilador supone que tu programa no tiene UB. Si una línea solo puede ser verdad con UB, la trata como imposible y optimiza a partir de ahí. cppreference lo dice así: como los programas correctos no tienen UB, con la optimización activada un programa que sí lo tiene puede dar «resultados inesperados».

Míralo de verdad. Esta función pregunta si a x le cabe uno más:

#include <climits>
#include <iostream>
using namespace std;

bool cabeUnoMas(int x) {
    int siguiente = x + 1;     // si x == INT_MAX, esto desborda: UB
    return siguiente > x;
}

int main() {
    cout << boolalpha << cabeUnoMas(INT_MAX) << "\n";
}

El mismo código, dos niveles de optimización:

$ g++ -std=c++17 -Wall -O0 ub.cpp -o ub && ./ub
false
$ g++ -std=c++17 -Wall -O2 ub.cpp -o ub && ./ub
true

Con -O0 la suma da la vuelta (en la práctica, a un número negativo) y la comparación dice false. Con -O2, el compilador razona: «x + 1 > x es siempre verdad... si no hay desbordamiento, y el desbordamiento no puede pasar». El ensamblador de la función se queda en una sola instrucción útil, movl $1, %eax: devolver true sin sumar nada. Ninguno de los dos resultados es «el correcto»: con UB no existe un resultado correcto.

Un caso más extremo

int main() {
    int vueltas = 0;
    for (int i = INT_MAX - 3; i > 0; i++) {   // i++ acaba desbordando: UB
        vueltas++;
        if (vueltas == 10) break;             // freno de seguridad
    }
    cout << vueltas << "\n";
}
$ g++ -std=c++17 -Wall -O0 bucle.cpp -o bucle && ./bucle
4
$ g++ -std=c++17 -Wall -O2 bucle.cpp -o bucle && ./bucle
Violación de segmento (`core' generado)

Con -O2, g++ ve que todo camino de main llega al desbordamiento (el freno está en 10 y el desbordamiento llega en la vuelta 4). Como «eso no puede pasar», concluye que main nunca se ejecuta... y no genera código para ella: en el ensamblador, main está vacía. El procesador sigue de largo y se estrella. Ni un aviso al compilar.

Error típico: «en mi máquina funciona». Con UB, que funcione hoy no demuestra nada. Cambia el nivel de optimización, la versión del compilador o una línea de al lado, y el resultado cambia. En el miniproyecto de esta lección, el ejercicio sin resolver compilado con -O2 no da ✗: repite las pruebas sin fin, porque un bucle con UB hizo que el programa saltara de vuelta al principio. Con UB, la única opción segura es quitarlo.

3. Cómo cazarlo

No se caza mirando la salida. Se caza con herramientas que vigilan mientras el programa corre (los sanitizers de la lección 4.8):

$ g++ -std=c++17 -Wall -g -fsanitize=undefined ub.cpp -o ub && ./ub
ub.cpp:6:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
false

Archivo, línea, columna y qué pasó. Cada sanitizer vigila una familia:

OpciónCaza
-fsanitize=undefined (UBSan)desbordamiento con signo, índice fuera de un arreglo de tamaño conocido, nullptr... Avisa y sigue
-fsanitize=address (ASan)usar tras liberar, salirse del montón, fugas. Se detiene en el primero
-fsanitize=thread (TSan)carreras de datos (lección 6.1). No se combina con address

Y una novedad de g++ 15: sin optimizar (-O0), la biblioteca estándar comprueba v[i] por ti (GCC 15 — Changes: «Debug assertions are now enabled by default for unoptimized builds»). Con vector<int> v = {1, 2, 3}; y cout << v[i]; con i valiendo 3:

$ g++ -std=c++17 -Wall -O0 rango.cpp -o rango && ./rango
.../stl_vector.h:1263: ... Assertion '__n < this->size()' failed.
Abortado (`core' generado)
$ g++ -std=c++17 -Wall -O2 rango.cpp -o rango && ./rango
0

Con -O2 esa comprobación se quita (g++ sí avisó al compilar, con -Warray-bounds) y el programa imprime basura tan tranquilo. Por eso: desarrolla y prueba con -g -fsanitize=address,undefined, y deja -O2 para cuando ya no haya UB y quieras velocidad.

4. La otra cara: la caché

Cambiamos de tema: ahora el programa es correcto y queremos que vaya rápido. La primera idea que hay que tener es que leer de la memoria principal (RAM) es lento comparado con lo que tarda el procesador en sumar. Por eso el procesador tiene una caché: una memoria pequeña y muy rápida pegada a él.

El truco de la caché: cuando pides un int, no trae solo ese. Trae el bloque entero donde está, una línea de caché (en esta máquina, 64 bytes: getconf LEVEL1_DCACHE_LINESIZE). Si el siguiente dato que pides está en ese mismo bloque, ya está ahí: gratis. A eso se le llama localidad: usar lo que está al lado de lo que acabas de usar.

Dos consecuencias que se miden:

  • Matriz por filas o por columnas. En un vector<vector<int>>, cada fila es un bloque seguido. Recorrer m[f][c] con c en el bucle de dentro va de vecino en vecino. Con f dentro, cada paso salta a otra fila.
  • vector o list. El vector guarda todo seguido. La list son nodos sueltos en el montón unidos por apuntadores (lección 3.4): cada nodo puede estar en cualquier sitio.

5. Medir sin engañarse

Ya mediste con <chrono> en la lección 3.8. Para que el número signifique algo, tres reglas:

  1. Compila con -O2. Sin optimizar mides otra cosa. En esta máquina, la suma por filas tardó 136 ms con -O0 y unos 5 ms con -O2.
  2. Repite y quédate con la mediana. Una sola medida mezcla tu código con lo que hacía el sistema en ese momento.
  3. Usa el resultado. Si no imprimes lo que calculas, el optimizador puede borrar el cálculo entero.
template <typename F>
double medir(F f, long long& resultado) {           // mediana de 7 repeticiones, en ms
    vector<double> tiempos;
    for (int r = 0; r < 7; r++) {
        auto inicio = chrono::steady_clock::now();
        resultado = f();
        auto fin = chrono::steady_clock::now();
        tiempos.push_back(chrono::duration<double, milli>(fin - inicio).count());
    }
    sort(tiempos.begin(), tiempos.end());
    return tiempos[tiempos.size() / 2];
}

long long r, control = 0;
cout << medir([&] { return porFilas(m); }, r) << " ms\n";
control += r;                                        // ...y al final: cout << control

Error típico: medir algo que el compilador ya borró. La primera versión de esta medición no usaba r. Resultado con -O2: unas 0.00003 ms para sumar 16 millones de números. No era la caché: g++ vio que el resultado no se usaba y quitó el bucle. Si una medida parece demasiado buena, desconfía.

Los resultados, en esta máquina (Intel Core i7-13700H, g++ 15.2, -O2, mediana de 7 repeticiones; tres ejecuciones del programa, de ahí los rangos):

QuéTiempoComparado
matriz 4000×4000, por filas4 a 7 msla referencia
la misma, por columnas55 a 100 msunas 11 a 18 veces más lenta
vector<int> de 10 millones, recorrer5 a 9 msla referencia
list<int> de 10 millones, nodos creados en orden22 a 35 msunas 4 veces más lenta
la misma list después de l.sort()1160 a 1560 msunas 150 a 240 veces más lenta

Las dos sumas por filas y por columnas hacen exactamente las mismas operaciones: misma O grande. Solo cambia el orden en que se visita la memoria. Y fíjate en la última fila: la lista recién creada aún tiene sus nodos casi seguidos en el montón (se pidieron uno detrás de otro). l.sort() reengancha los nodos sin moverlos, así que recorrerla en orden significa saltar por todo el montón. Así queda una lista real después de mucho insertar y borrar.

Los números exactos cambiarán en tu ordenador. Lo que no cambia es el orden de magnitud: la memoria contigua gana. Por eso vector es el contenedor por defecto aunque la O grande de list parezca mejor para algunas cosas.

6. Perfilar (opcional)

Medir con <chrono> responde «¿cuánto tarda esto?». Un perfilador responde «¿dónde se va el tiempo?» en un programa entero. Dos que existen en Linux:

  • gprof: compila con -pg, ejecuta, y luego gprof -b prog gmon.out muestra qué funciones gastaron más tiempo. Funciona en esta máquina.
  • perf: más potente (puede contar fallos de caché). Necesita permisos del sistema; en esta máquina, sin ellos, se niega (perf wiki).

Con lo que sabes ya basta para este curso. Si algún día optimizas en serio: primero mide, luego cambia, luego vuelve a medir.

¿Qué pasa en la memoria?

El procesador no lee la RAM de int en int: trae líneas de 64 bytes a la caché. Una línea guarda 16 int (si sizeof(int) es 4, lo normal). Recorrer un vector aprovecha las 16; recorrer una list desordenada aprovecha una, porque cada nodo es un bloque aparte del montón (heap) con su dato y sus dos apuntadores.

vector (montón)
[1|2|3|4|5|6...]
una línea trae 16 seguidos
list (montón)
[3]→ ... [1]→ ... [2]
cada nodo, quizá otra línea

En vector<vector<int>>, cada fila es su propio bloque del montón. Por filas lees un bloque de principio a fin; por columnas tomas un int de cada fila y saltas a la siguiente. Y el UB del miniproyecto también es memoria: en struct Alumno { int notas[3]; int edad; }, notas[3] no existe, pero en la práctica lee la caja de al lado, la edad.
