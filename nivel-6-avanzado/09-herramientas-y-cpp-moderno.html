Herramientas profesionales y C++ moderno

Probar, depurar y revisar tu código como en un equipo de verdad, y un vistazo a corrutinas y módulos. ~40 minutos.

Al terminar podrás: escribir tus propias pruebas unitarias con un mini marco de macros, encontrar con gdb la línea exacta donde se cae un programa, vigilar una variable hasta que cambie, pedirle al compilador que revise tu código sin ejecutarlo, y reconocer una corrutina (co_yield) y un módulo (import) cuando los veas.

Antes de empezar: repite sin mirar el quiz de la lección 6.8 (comportamiento indefinido y rendimiento). Es el último calentamiento del curso.

Por qué. En todo el curso, cada miniproyecto traía sus pruebas hechas: la función comprobar() con sus ✓ y ✗. En un trabajo real, esas pruebas las escribes tú. Y cuando algo se cae, nadie te dice la línea: la encuentras con un depurador. Esta lección junta las herramientas que usa un profesional cada día. La lección 4.8 ya te dio el mapa (gdb básico, sanitizers, CMake, estándares); aquí bajamos al detalle y no lo repetimos.

Compila con g++ -std=c++17 -Wall -pthread. Solo el ejemplo de corrutinas (sección 8) necesita -std=c++23, y lo digo allí.

1. Una prueba unitaria es código que comprueba código

Una prueba unitaria comprueba una pieza pequeña (una función, una clase) por separado. LearnCpp lo explica con un coche: pruebas cada pieza antes de montarla, no el coche entero al final (LearnCpp 9.1). Si una prueba falla, el error está en esa pieza, no en todo el programa.

Ya conoces una forma: assert(cond) corta el programa si cond es falsa. Sirve para avisar de errores del programador, pero tiene dos problemas como marco de pruebas: se detiene en el primer fallo y desaparece si compilas con -DNDEBUG (cppreference — assert). Un marco de pruebas hace lo contrario: ejecuta todas las comprobaciones, cuenta los fallos y dice dónde está cada uno.

2. Tu propio marco de pruebas, con macros

La función comprobar(ok, "texto") de los ejercicios tiene una pega: el texto lo escribes a mano. Queremos que el fallo diga solo qué expresión falló y en qué línea. Una función no puede saberlo. Una macro sí, porque el preprocesador trabaja con el texto del código antes de compilar. Tres piezas:

PiezaQué da
#x (dentro de una macro)el argumento x convertido en texto: "2 + 3"
__FILE__el nombre del archivo, como texto
__LINE__el número de línea, como int
#define MOSTRAR(expr) std::cout << #expr << " = " << (expr) << "\n"

MOSTRAR(2 + 3);       // muestra: 2 + 3 = 5
MOSTRAR(__LINE__);    // muestra: __LINE__ = y el número de esta línea

Con eso, la macro de pruebas sale en una línea. La macro solo «captura» el texto y la línea; el trabajo lo hace una función normal:

int esperasHechas = 0, esperasFallidas = 0;

void anotar(bool ok, const string& mensaje) {
    esperasHechas++;
    if (!ok) { esperasFallidas++; cout << mensaje << "\n"; }
}

#define ESPERAR_VERDAD(cond) \
    anotar((cond), string(__FILE__) + ":" + to_string(__LINE__) + ": ESPERAR_VERDAD(" #cond ") falló")

Pila p;
ESPERAR_VERDAD(p.vacia());       // pasa: no muestra nada
p.push(1);
ESPERAR_VERDAD(p.vacia());       // pila.cpp:14: ESPERAR_VERDAD(p.vacia()) falló

(Salida real: en el archivo completo, esa llamada está en la línea 14.)

La \ al final de la línea dice «la macro sigue abajo». Y fíjate en " ... (" #cond ") falló": tres textos seguidos se pegan en uno solo.

En el miniproyecto completarás dos macros más: ESPERAR_IGUAL(a, b), que además dice cuánto valía cada lado, y ESPERAR_LANZA(expr, Tipo), que comprueba que algo lanza una excepción (lección 4.4). Son las mismas que tienen los marcos profesionales, con otro nombre.

Las macros pegan texto, no valores. No saben de prioridad de operadores:

#define CUADRADO(x) x * x
cout << CUADRADO(2 + 3);    // muestra 11, no 25: se pega «2 + 3 * 2 + 3»

Regla: dentro de la macro, pon cada argumento entre paréntesis ((x) * (x)), úsalo una sola vez (si escribes CUADRADO(i++), se incrementaría dos veces) y deja el trabajo a una función. Usa macros solo para lo que una función no puede hacer: el texto y la línea.

En C++20 hay otra vía para la línea: std::source_location. Un parámetro por defecto std::source_location donde = std::source_location::current() recibe el archivo y la línea de quien llama (cppreference — source_location). Lo que todavía no da es el texto de la expresión; para eso sigue haciendo falta #.

3. Pruebas que de verdad pueden fallar

Una prueba que nunca falla no protege nada. ESPERAR_IGUAL(p.tamano(), p.tamano()) compila, pasa siempre... y no comprueba nada. Tres hábitos:

  • Una idea por bloque. «Una pila nueva está vacía», «top devuelve el último», «pop sobre vacía lanza». Cada una en su { Pila p; ... }, para que no dependan unas de otras.
  • Casos borde. Vacía, un solo elemento, el primero y el último. Ahí se esconden casi todos los errores de listas, pilas y colas.
  • Rómpelo a propósito. Cambia una línea de la clase (por ejemplo, que pop() no descuente el tamaño) y mira si alguna prueba se pone en rojo. Si ninguna lo nota, te falta una prueba. A esto se le llama mutation testing (pruebas por mutantes), y es justo lo que hace el corrector del miniproyecto.

6. Análisis estático: revisar sin ejecutar

Los sanitizers (lecciones 4.8 y 6.8) son análisis dinámico: vigilan el programa mientras corre, así que solo ven los caminos que se ejecutan. El análisis estático lee el código sin ejecutarlo y busca caminos peligrosos.

El primero ya lo usas: los avisos del compilador. -Wall -Wextra es análisis estático gratis. Trata cada aviso como un error.

GCC trae un analizador más profundo: -fanalyzer. Este código tiene una fuga en el camino del return 0; con -Wall -Wextra no sale ningún aviso, pero con -fanalyzer (salida real, recortada):

int primero(Nodo* cabeza) {
    Nodo* n = new Nodo{1, nullptr};
    if (cabeza == nullptr) return 0;   // olvidé el delete aquí
    int d = n->dato + cabeza->dato;
    delete n;
    return d;
}
g++ -std=c++17 -Wall -Wextra -fanalyzer -c fuga.cpp
fuga.cpp:5:35: warning: leak of ‘n’ [CWE-401] [-Wanalyzer-malloc-leak]
    5 |     if (cabeza == nullptr) return 0;   // olvidé el delete aquí
    4 |     Nodo* n = new Nodo{1, nullptr};
      |                                  (1) allocated here
      ...
      |                                   (6) ‘n’ leaks here; was allocated at (1)

Te dibuja el camino: dónde se reservó, qué rama tomó y dónde se perdió. Un aviso honesto: la documentación de GCC dice que el analizador solo es adecuado para código C en esta versión (GCC — Static Analyzer Options). Con C++ encuentra cosas como esta, pero no esperes que lo vea todo.

Las herramientas de verdad para C++ (opcionales; no están instaladas en tu máquina):

  • clang-tidy: un linter de C++ basado en Clang. Encuentra errores típicos de estilo y de programación, y muchos los arregla solo. Uso: clang-tidy pila.cpp -- -std=c++17 (lo que va tras -- son las opciones de compilación).
  • Cppcheck: herramienta de análisis estático para C y C++, centrada en errores reales (fuera de rango, fugas...). Uso: cppcheck pila.cpp o cppcheck --enable=style pila.cpp.

8. Corrutinas: funciones que se pausan

Una función normal empieza, termina y olvida todo. Una corrutina es una función que puede pausarse a la mitad, devolver el control a quien la llamó y seguir después donde se quedó (cppreference — Coroutines). Se reconoce porque usa co_yield, co_await o co_return.

El uso más fácil es un generador: una función que entrega valores uno a uno, a demanda. C++23 trae std::generator (cppreference — std::generator), y con g++ 15 y -std=c++23 funciona. Este programa está compilado y ejecutado:

#include <generator>
#include <print>
#include <ranges>

std::generator<long long> fibonacci() {
    long long a = 0, b = 1;
    while (true) {           // infinito: no pasa nada
        co_yield a;          // entrega a y se pausa AQUÍ
        long long sig = a + b;
        a = b;
        b = sig;
    }
}

int main() {
    for (long long x : fibonacci() | std::views::take(8))
        std::print("{} ", x);
    std::println("");
}
g++ -std=c++23 -Wall fibonacci.cpp -o prog && ./prog
0 1 1 2 3 5 8 13

Fíjate en el while (true): no se cuelga porque el generador es perezoso. Cada vuelta del for le pide un valor; la función corre hasta el siguiente co_yield y se pausa. take(8) (lección 6.5) deja de pedir al octavo, y ahí acaba todo. Hasta crear el generador es perezoso: auto g = fibonacci(); no ejecuta ni una línea de su cuerpo.

El otro gran uso, co_await, sirve para programas asíncronos (esperar a la red o al disco sin bloquear un hilo). Para eso el estándar da solo las piezas de bajo nivel; en la práctica se usa una biblioteca. Queda fuera de este curso.

9. Módulos: el sustituto de #include

#include es «pega aquí el archivo entero» (lección 4.6). Por eso los proyectos grandes compilan lento: cada .cpp vuelve a leer los mismos .h. Un módulo se compila una vez, y quien lo usa lo importa; además, solo se ve lo que el módulo marca con export (cppreference — Modules).

// saludo.cpp — el módulo
export module saludo;            // este archivo ES el módulo «saludo»

export int doble(int x) { return 2 * x; }   // export: se ve desde fuera
int secreto() { return 42; }                // sin export: privado

// main.cpp — quien lo usa
import saludo;
import std;                      // C++23: TODA la biblioteca estándar de una vez
int main() { std::println("{}", doble(21)); }   // muestra 42

Estado del soporte (comprobado con g++ 15.2 en esta máquina):

  • Funciona, pero hay que pedirlo: -std=c++20 no basta, hace falta -fmodules (GCC — C++ Modules). Y el orden importa: primero se compila el módulo y después quien lo importa.
  • import std; necesita compilar antes la biblioteca estándar como módulo: g++ -std=c++23 -fmodules -fsearch-include-path -c bits/std.cc (tardó unos 4,5 s). Después, main.cpp compiló y mostró 42; llamar a secreto() dio ‘secreto’ was not declared in this scope.
  • La tabla de cppreference marca los módulos de C++20 en GCC como «parcial» desde GCC 11, e import std desde GCC 15 (cppreference — compiler support). CMake los admite desde la versión 3.28, y import std solo con GCC 15 o más nuevo y el generador Ninja (CMake — cxxmodules).

Conclusión: son el futuro y ya funcionan, pero todavía exigen opciones especiales y herramientas recientes. Para tus tareas y proyectos de hoy, sigue con .h y .cpp como en la 4.6. No hay ejercicio de módulos.

¿Qué pasa en la memoria?

gdb te deja ver el mapa de la memoria que has imaginado todo el curso. bt es la lista de marcos de la memoria automática (la pila de llamadas o stack), uno por renglón: top encima de balanceado, encima de main. Y las direcciones de la sesión 5.3 lo confirman: la Pila p, local de main, estaba en 0x7fffffffd740; los Nodo, creados con new, en 0x55555556e050. En Linux, normalmente, la memoria automática queda en direcciones altas y el montón (heap) mucho más abajo.

Cómo seguir después del curso

Aquí termina el temario. Lo que toca ahora es practicar con un proyecto tuyo, pequeño y terminado. Para elegirlo, vuelve a la lección 4.8: la sección 6 tiene rutas según lo que te guste (juegos, embebidos, sistemas, programación competitiva), la 7 los libros y recursos, y la 8 las comunidades donde preguntar. Y llévate tres hábitos de esta lección a cualquier proyecto: escribe pruebas mientras programas, compílalas con -fsanitize=address,undefined y, cuando algo se caiga, abre gdb antes de llenar el código de cout.

¿Algo no quedó claro? Pregúntame en el chat lo que sea: una línea que no entiendes, un error de compilación o «explícamelo de otra forma». Y si eliges un proyecto para seguir, cuéntamelo: podemos preparar juntos sus primeras pruebas.

Terminaste el curso. Empezaste con cout << "Hola" y acabas escribiendo las pruebas de tu propia Pila, depurándola con gdb y leyendo corrutinas de C++23. Lo que queda es practicar con proyectos tuyos.
