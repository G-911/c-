Plantillas avanzadas y concepts

Plantillas que deciden al compilar y avisan claro cuando las usas mal. ~40 minutos.

Al terminar podrás: escribir una función que acepta cualquier número de argumentos, elegir código según el tipo con if constexpr, calcular cosas al compilar con constexpr, y poner un concept a tus plantillas para que un mal uso dé un error de una línea en vez de un muro de texto.

Antes de empezar: repite sin mirar el quiz de la lección 6.3 (categorías de valor y reenvío). Y ten a mano tu Pila<T> y tu maximo de la lección 4.1: hoy los mejoramos.

Por qué. En la 4.1 aprendiste que una plantilla es un molde y que «lo que el cuerpo le haga a T, el tipo tiene que saber hacerlo». Pero nada lo comprobaba: si te equivocabas, el error salía dentro de la plantilla. Hoy ves las herramientas con las que está escrita la biblioteca estándar moderna: especializar, aceptar «cualquier número de argumentos», preguntar por el tipo al compilar y, sobre todo, declarar lo que la plantilla pide. No es metaprogramación compleja (eso queda fuera del curso): son cinco piezas que vas a leer en cualquier código C++ actual.

Compila con g++ -std=c++20 -Wall -pthread: los concept son de C++20 (lo demás funciona desde C++17).

1. Especialización total: una versión a medida

A veces el molde general sirve para casi todo, pero un tipo concreto necesita otro código. Se escribe la versión general y luego, con template <>, la de ese tipo:

template <typename T>
string describir(T) { return "algo"; }           // la general

template <>
string describir<bool>(bool b) {                // solo para bool
    return b ? "sí" : "no";
}

cout << describir(5) << " " << describir(true);   // algo sí

template <> con los <> vacíos significa «ya no queda ningún tipo por decidir»: es una especialización total. Con clases es igual:

template <typename T>
struct NombreDe { static string valor() { return "desconocido"; } };

template <>
struct NombreDe<int> { static string valor() { return "int"; } };

cout << NombreDe<int>::valor() << " " << NombreDe<double>::valor();   // int desconocido

Con funciones, muchas veces basta una sobrecarga normal. Donde la especialización brilla es con clases. El ejemplo clásico: para usar tu propio tipo como clave de un unordered_map (las tablas hash de la lección 5.6) se especializa std::hash<TuTipo> (LearnCpp 26.4).

2. Plantillas variádicas: cualquier número de argumentos

Ya viste Args&&... args en la lección anterior. Los tres puntos declaran un paquete (parameter pack): cero, uno o muchos tipos.

template <typename... Args>            // Args: un paquete de TIPOS
void imprimirTodo(const Args&... args) { // args: un paquete de VALORES
    cout << sizeof...(args) << " argumentos\n";
}

imprimirTodo(1, "hola", 2.5);   // 3 argumentos  (Args = int, const char*, double)
imprimirTodo();                 // 0 argumentos

Un paquete no se recorre con un for: se expande. La forma más cómoda de expandirlo es una expresión de pliegue (fold expression, C++17): pones el paquete, un operador y ..., y el compilador repite la operación para cada elemento.

template <typename... Args>
auto sumaTodo(const Args&... args) {
    return (0 + ... + args);        // ((0 + a1) + a2) + a3
}

template <typename... Args>
void imprimirTodo(const Args&... args) {
    ((cout << args << ' '), ...);   // repite (cout << arg << ' ') con la coma
    cout << '\n';
}

cout << sumaTodo(1, 2, 3);          // 6
cout << sumaTodo(1, 2.5);           // 3.5
imprimirTodo(1, "hola", 2.5);       // 1 hola 2.5

Hay cuatro formas; los paréntesis de fuera son obligatorios (cppreference — Fold expressions):

EscribesSe expande aNombre
(args + ...)a1 + (a2 + a3)unario por la derecha
(... + args)(a1 + a2) + a3unario por la izquierda
(args + ... + 0)a1 + (a2 + (a3 + 0))binario por la derecha
(0 + ... + args)((0 + a1) + a2) + a3binario por la izquierda

Paquete vacío. (args + ...) con cero argumentos no compila (fold of empty expansion over operator+): no hay nada que sumar y el compilador no se inventa un 0. Solo tres operadores tienen valor por defecto con el paquete vacío: && (true), || (false) y la coma. Para lo demás, usa la forma binaria con un valor inicial: (0 + ... + args).

3. Rasgos de tipo: preguntar por T

<type_traits> trae «preguntas» sobre tipos que se responden al compilar. Cada una es un bool constante:

PreguntaVerdadero para
is_integral_v<T>int, long, char, bool...
is_floating_point_v<T>float, double, long double
is_same_v<T, U>si T y U son el mismo tipo
is_pointer_v<T>int*, Nodo*...
is_arithmetic_v<T>enteros y de coma flotante

Fíjate: char y bool cuentan como enteros. Se usan, por ejemplo, con static_assert, que comprueba algo al compilar y, si falla, detiene la compilación con tu mensaje:

template <typename T>
T mitad(T x) {
    static_assert(is_arithmetic_v<T>, "mitad() solo admite números");
    return x / 2;
}

Esa era la forma de «poner condiciones» a una plantilla antes de C++20. Los concepts de la sección 6 lo hacen mejor.

4. if constexpr: elegir código según el tipo

Quieres convertir cualquier cosa a texto: un string se devuelve tal cual, un número se pasa por to_string. Con un if normal no compila:

template <typename T>
string aTexto(const T& x) {
    if (is_same_v<T, string>) return x;
    else return to_string(x);      // con T = string: to_string(string) no existe → error
}

Un if normal decide al ejecutar, así que las dos ramas tienen que compilar para cada T. Con T = string falla la segunda; con T = int, la primera. if constexpr decide al compilar, y la rama descartada ni siquiera se instancia:

template <typename T>
string aTexto(const T& x) {
    if constexpr (is_same_v<T, string>) return x;
    else return to_string(x);
}

cout << aTexto(42) << " " << aTexto(string("hi"));   // 42 hi

La condición tiene que poder calcularse al compilar: rasgos de tipo, sizeof, constantes. No sirve para variables normales (LearnCpp 8.4 — Constexpr if statements). Y solo descarta ramas dentro de una plantilla: fuera de ellas, las dos ramas se comprueban igual (cppreference — if).

5. constexpr y consteval: calcular al compilar

Una función constexpr puede ejecutarse al compilar si sus argumentos se conocen entonces. Si no, se ejecuta normal, al correr el programa:

constexpr long long factorial(int n) {
    long long r = 1;
    for (int i = 2; i <= n; i++) r *= i;
    return r;
}

static_assert(factorial(5) == 120);   // comprobado AL COMPILAR: si fallara, no compila
constexpr long long f = factorial(5); // f ya vale 120 dentro del ejecutable

int n;
cin >> n;
cout << factorial(n);                 // también vale: aquí se calcula al ejecutar

consteval (C++20) es más estricta: la función tiene que calcularse al compilar. Llamarla con algo que solo se sabe al ejecutar es un error (LearnCpp F.3):

consteval int cuadrado(int n) { return n * n; }

constexpr int c = cuadrado(4);   // bien: 16
int n = 4;
cuadrado(n);                     // error: call to consteval function is not a constant expression
PalabraSe calcula
constexpr (función)al compilar si puede; si no, al ejecutar
constevalsiempre al compilar; si no puede, error
constexpr (variable)obliga a que su valor se conozca al compilar
static_assert(cond)comprueba cond al compilar

6. Concepts: decir qué pide la plantilla

Este es el gran cambio de C++20. Toma una plantilla del estilo de la 4.1, que calcula el promedio de un vector, y úsala mal, con un tipo que no se puede sumar ni dividir:

struct Punto { int x, y; };

template <typename T>
T sumar(const vector<T>& v) {
    T suma{};
    for (const T& e : v) suma += e;
    return suma;
}

template <typename T>
T promedio(const vector<T>& v) {
    return sumar(v) / v.size();
}

int main() {
    vector<Punto> puntos = {{1, 2}, {3, 4}};
    promedio(puntos);
}

Esto es lo que dice g++ 15 de verdad, guardado como sin-concepts.cpp (arriba lleva los #include y el using, por eso Punto está en la línea 5). Recortado: «…» marca lo quitado.

Dos errores, y los dos señalan dentro de la plantilla (líneas 10 y 16), no tu línea 21. Si la plantilla fuera de una biblioteca, te estaría hablando de un operator+= en un archivo que no escribiste. Con plantillas que llaman a otras plantillas, esa cadena de required from crece y crece. Ahora pon un concept:

template <typename T>
concept Numerico = is_integral_v<T> || is_floating_point_v<T>;

template <Numerico T>               // antes: template <typename T>
T promedio(const vector<T>& v) { ... }   // (y lo mismo en sumar)

Hay varias notas, pero un solo error, en tu línea 25, y dice exactamente qué regla no se cumple: «Punto no es Numerico: no es entero ni de coma flotante». El compilador ya no entra en el cuerpo: rechaza la llamada en la puerta. Esa es la ventaja de verdad: el error habla de lo que pide la plantilla, no de dónde reventó. Además, el concept documenta el contrato en la propia firma (cppreference — Constraints and concepts).

Tres formas de escribirlo (equivalentes)

template <Numerico T>                       T doble(T x)   { return x * 2; }   // 1. en lugar de typename
template <typename T> requires Numerico<T>  T mitad(T x)   { return x / 2; }   // 2. cláusula requires
auto triple(Numerico auto x)                               { return x * 3; }   // 3. abreviada

Pedir operaciones, no tipos: requires como expresión

Un concept también puede decir «lo que sea, con tal de que tenga .size()». Escribes un trozo de código de ejemplo; el concept se cumple si ese código compilaría:

template <typename T>
concept TieneTamano = requires(T c) {
    c.size();                    // «c.size() tiene que ser válido»
};

cout << TieneTamano<string> << TieneTamano<int>;   // 10

Y no hace falta inventarlos todos: <concepts> trae los habituales, como std::integral, std::floating_point o std::totally_ordered (se puede comparar con <, >, ==...). Tu maximo de la 4.1 queda así:

template <std::totally_ordered T>
T maximo(T a, T b) { return (a > b) ? a : b; }

Un concept no revisa el cuerpo. Solo comprueba la llamada contra lo que declaraste. Si pides TieneTamano y en el cuerpo usas también c.front(), un tipo con size() pero sin front() pasa la puerta y vuelve el error largo de antes, dentro de la plantilla. El concept tiene que pedir todo lo que el cuerpo usa.

¿Qué pasa en la memoria?

Casi todo lo de esta lección ocurre al compilar y no deja nada en ejecución. Un concept, un is_integral_v o un static_assert no ocupan ni un byte del programa: son preguntas que el compilador responde y olvida. Con constexpr long long f = factorial(5); en el ejecutable solo queda el número 120; la función no llega a ejecutarse, y no hay ningún marco en la memoria automática (la pila de llamadas o stack) para ella.

zona de código
imprimirTodo<int, const char*, double>
imprimirTodo<>
una versión por lista de tipos
al compilar
Numerico, static_assert
0 bytes en ejecución

Lo que sí existe son las versiones que se fabrican, como en la 4.1: cada lista distinta de tipos con que llamas a imprimirTodo genera su propia función en la zona de código. Y con if constexpr cada versión lleva solo su rama: la descartada no se compila, así que tampoco ocupa sitio. Nada de esto toca el montón.

Miniproyecto 6.4 · Plantillas que saben lo que piden

Abre ejercicios/04-plantillas-avanzadas-y-concepts.cpp. Son seis piezas pequeñas, una por sección. Completa:

  1. Dos especializaciones totales de nombreDeTipo<T>(), para int y double.
  2. unirConEspacios(args...): cada argumento seguido de un espacio, con un fold.
  3. sumaTodo(args...): que dé 0 con cero argumentos.
  4. El concept Numerico (ahora dice true para todo).
  5. describir(x) con if constexpr: «entero», «decimal», «texto» u «otro».
  6. factorial(n) constexpr. Extra: descomenta el static_assert.

Compílalo desde la carpeta ejercicios:

g++ -std=c++20 -Wall -pthread 04-plantillas-avanzadas-y-concepts.cpp -o prog && ./prog
