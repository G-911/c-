Excepciones

Cuando algo sale mal, avisar en voz alta en lugar de callarse. ~35 minutos.

Al terminar podrás: hacer que pop() y top() de tu Pila lancen std::out_of_range si está vacía, y atrapar ese error con try/catch sin que el programa se caiga.

Antes de empezar: repite sin mirar el quiz de la lección 4.3 (algoritmos y lambdas). Recordar lo de ayer es lo que hace que se quede.

Por qué. En la lección 3.6 tu pop() sobre una pila vacía no hacía nada, y top() tenía una «precondición»: si la pila estaba vacía, desreferenciaba nullptr. Las dos cosas esconden el error. Un programa serio avisa. Así funciona la biblioteca estándar (vector::at, stoi...) y así se espera que funcione tu código a nivel intermedio-avanzado.

1. El problema: callarse o caerse

Mira la Pila del Nivel 3:

int top() const { return tope->dato; }   // vacía: tope es nullptr → se cae

void pop() {
    if (vacia()) return;                   // vacía: no hace nada, nadie se entera
    ...
}

¿Y si top() devolviera -1 cuando está vacía? Tampoco sirve: -1 puede ser un dato válido de la pila. No hay ningún int «especial» libre para decir «error».

La solución de C++ es otra vía de salida, aparte del return: la excepción.

2. throw, try y catch

  • throw lanza un error. La función se corta ahí mismo.
  • try { ... } marca un trozo de código «vigilado».
  • catch (...) { ... } atrapa el error y decide qué hacer.
#include <stdexcept>   // runtime_error, out_of_range, invalid_argument

try {
    cout << "A";
    throw runtime_error("algo salió mal");   // salta directo al catch
    cout << "B";                             // esta línea NUNCA se ejecuta
} catch (const runtime_error& e) {
    cout << "C: " << e.what();              // what() devuelve el mensaje
}
cout << "D";
// Muestra: AC: algo salió malD

El throw puede estar muy lejos del catch: dentro de una función, que la llama otra función, que la llama main. El error «sube» por la pila de llamadas (la que viste en la lección 3.1) hasta el primer catch que le sirva.

Si nadie lo atrapa, el programa termina. Un throw sin ningún catch que le sirva llama a std::terminate(): el programa se corta en seco (LearnCpp 27.4). Lanzar no arregla nada por sí solo: alguien tiene que atrapar.

3. Las excepciones de la biblioteca estándar

No hace falta inventar tus propios tipos de error. <stdexcept> trae varios, todos hijos de std::exception (herencia, lección 2.5):

TipoÚsalo cuando...
out_of_rangepides algo fuera de rango: un índice que no existe, el tope de una pila vacía
invalid_argumentte pasan un argumento que no tiene sentido (dividir entre 0)
runtime_errorfalla algo que solo se sabe al ejecutar (un archivo que no abre)
exceptionno lo lances tú; sirve para atrapar cualquiera de los de arriba

Ya te has cruzado con uno: vector::at lanza out_of_range cuando el índice no existe (cppreference). Por eso en la lección 1.8 era más seguro que [].

vector<int> v = {1, 2};
try {
    cout << v.at(5);
} catch (const out_of_range& e) {
    cout << "fuera de rango";               // esto es lo que se ve
}

Fíjate en const ... &: se atrapa por referencia constante. Así no se copia el error y, si atrapas un tipo padre (exception), sigues viendo el mensaje del hijo.

4. La Pila que avisa

Este es el cambio de toda la lección. Dos líneas:

int top() const {
    if (vacia()) throw out_of_range("top: la pila vacía no tiene tope");
    return tope->dato;
}

void pop() {
    if (vacia()) throw out_of_range("pop: la pila vacía no tiene tope");
    Nodo* viejo = tope;          // lo de siempre (lección 3.6)
    tope = tope->siguiente;
    delete viejo;
}

Y quien la usa decide qué hacer con el error:

Pila p;
try {
    p.pop();
} catch (const out_of_range& e) {
    cout << "Error: " << e.what() << "\n";   // Error: pop: la pila vacía no tiene tope
}
p.push(7);                                     // la pila sigue sana: el throw no tocó nada

Fíjate en el orden: se comprueba antes de tocar nada. Si lanzas a mitad de cambio (con el tope ya movido, por ejemplo), la pila queda rota.

5. Varios catch: el orden importa

Puedes poner varios catch seguidos. C++ los prueba de arriba abajo y usa el primero que encaje. Por eso el más concreto va primero:

try {
    hacerAlgo();
} catch (const out_of_range& e) {      // 1.º el concreto
    cout << "rango: " << e.what();
} catch (const exception& e) {         // 2.º el general: atrapa el resto
    cout << "otro error: " << e.what();
} catch (...) {                         // 3.º atrapa CUALQUIER cosa
    cout << "error desconocido";
}

Error típico: poner el general primero.

catch (const exception& e)    { ... }   // atrapa TODO, también out_of_range
catch (const out_of_range& e) { ... }   // nunca llega aquí

Compila (g++ solo avisa con un warning), pero el segundo catch es código muerto. Y otro clásico: catch (exception e) sin & copia el error y pierde el tipo del hijo. Siempre const ... &.

6. Al lanzar, las variables locales se destruyen

Cuando la excepción sube, C++ va cerrando las funciones que abandona y destruye sus variables locales (llama a sus destructores). A eso se le llama «desenrollar la pila» (stack unwinding). Una Pila local, un vector o un string se liberan solos.

Pero un new suelto no es una variable local: lo local es el apuntador, no lo apuntado.

void f() {
    int* p = new int(5);
    hacerAlgo();          // si esto lanza...
    delete p;             // ...esta línea no se ejecuta: FUGA de memoria
}

Esto no tiene arreglo cómodo con new/delete a mano. Lo arregla la idea de la próxima lección: RAII y los apuntadores inteligentes, que liberan en el destructor.

7. ¿Excepción o código de error?

Las excepciones no sustituyen a todos los if. Regla práctica:

SituaciónMejorPor qué
pop() sobre pila vacíaexcepciónquien llama se equivocó; no hay valor que devolver
dividir entre 0, índice fuera de rangoexcepciónno se puede continuar con sentido
buscar(x) y x no estábool o -1no encontrar es un resultado normal, no un error
salir de un buclebreakusar excepciones para el flujo normal es lento y confuso

Una pregunta que ayuda: ¿quien llama puede seguir como si nada? Si sí, devuelve un valor. Si no, lanza.

¿Qué pasa en la memoria?

Cada llamada tiene su marco en la memoria automática (la pila de llamadas o stack). Cuando se lanza una excepción, C++ abandona los marcos uno por uno hasta llegar al catch, y en cada uno destruye los objetos locales en orden inverso al de su creación: eso es el desenrollado. Una Pila local, un vector o un string llaman a su destructor y devuelven su parte del montón.

marco de f (se abandona)
p →
se destruye p, no lo apuntado
en el montón
[5]
sin dueño: fuga
marco de main
catch (...)
aquí sigue el programa

En f(), lo que vive en el marco es p, un apuntador. Se destruye, pero destruir un apuntador no hace delete: el int del montón se queda sin dueño. Y el objeto de la excepción (el out_of_range con su mensaje) no vive en ninguno de los marcos que se abandonan: C++ lo guarda en un sitio aparte. Por eso e.what() sigue funcionando dentro del catch.

Abre ejercicios/04-excepciones.cpp. La Pila ya trae push, el destructor y un contador de nodos vivos. Completa:
