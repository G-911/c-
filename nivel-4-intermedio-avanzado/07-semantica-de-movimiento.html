Semántica de movimiento

Si el original ya no lo vas a usar, no lo copies: llévatelo. ~35 minutos.

Al terminar podrás: escribir el constructor de movimiento y la asignación por movimiento de tu Pila, saber cuándo usar std::move y explicar por qué devolver un vector enorme desde una función no cuesta casi nada.

Antes de empezar: repite sin mirar el quiz de la lección 4.6 (archivos y proyectos). Y si no recuerdas qué era la «regla de tres», dale un vistazo de 5 minutos a la lección 3.5: hoy la terminamos.

Por qué. En la lección 3.5 aprendiste a copiar una lista bien: nodo a nodo, copia profunda. Funciona, pero con un millón de nodos son un millón de new. Muchas veces el original ya no se va a usar: era un temporal, o lo vas a meter en un vector y olvidarte de él. Copiarlo es tirar trabajo. Mover es pasarle los nodos al nuevo dueño en un instante. Ya lo hiciste sin saberlo con unique_ptr y move en la lección 4.5; hoy ves cómo funciona por dentro. Es la idea que hizo que el C++ moderno (desde C++11) fuera rápido sin esfuerzo.

1. Copiar contra mover

Imagina que te mudas y un amigo se queda con tu biblioteca. Copiar es fotocopiar todos los libros: lento, y al final hay dos bibliotecas. Mover es darle la llave: instantáneo, y tú te quedas sin biblioteca. Si ya no la ibas a usar, lo segundo es obviamente mejor.

Con la Pila del Nivel 3, mover es copiar un solo apuntador, el tope, y dejar al original apuntando a nullptr:

Antes de Pila b = std::move(a);

a
tope → [3] → [2] → [1]
n = 3
b
(todavía no existe)

Después: los nodos son los mismos, no se creó ninguno.

a
tope = nullptr
n = 0 (vacía, pero válida)
b
tope → [3] → [2] → [1]
n = 3

Copiar cuesta lo que mida la pila: O(n). Mover cuesta siempre lo mismo: O(1). (Si no recuerdas la notación, está en la lección 3.8.)

2. ¿Cuándo es seguro robar? lvalue y rvalue

Robar los nodos de algo que alguien va a seguir usando sería un desastre. Así que C++ necesita distinguir dos clases de valores. La versión intuitiva:

TipoIdeaEjemplos
lvaluetiene nombre y sigue vivo después de esta línea; puedes pedir su dirección con &x, a, v[0]
rvalueun temporal sin nombre: muere al terminar la línea5, x + 1, crearPila(3)

Truco para recordarlo: si puedes escribir &cosa, es un lvalue. Un rvalue va a morir enseguida, así que nadie va a notar que le robaste el contenido. A un rvalue se le puede robar sin peligro. A un lvalue, no (salvo que tú lo autorices; ver sección 4).

3. &&: una referencia solo para temporales

En la lección 2.1 viste T& y const T&. C++11 añadió T&&, la referencia a rvalue: solo se engancha a temporales. Con ella puedes escribir dos versiones de una función y el compilador elige sola:

void recibir(const Pila& p) { cout << "copio\n"; }   // para lvalues
void recibir(Pila&& p)      { cout << "robo\n";  }   // para rvalues

Pila a;
recibir(a);              // "copio": a tiene nombre, sigue viva
recibir(crearPila(3));   // "robo":  es un temporal

El constructor de movimiento es exactamente eso: un constructor que recibe Pila&&.

4. std::move: «ya no lo voy a usar»

¿Y si tú sabes que una variable con nombre ya no te sirve? Se lo dices al compilador con std::move (en <utility>):

vector<Pila> lista;
Pila p = crearPila(1000);
lista.push_back(p);              // COPIA: 1000 new
lista.push_back(std::move(p));   // MUEVE: copia un apuntador. p queda vacía

Lo curioso: std::move no mueve nada. Solo convierte p en un rvalue (es un static_cast a Pila&&). Quien mueve de verdad es el constructor de movimiento, que ahora sí es el elegido (LearnCpp 22.4 — std::move).

No uses un objeto después de moverlo (salvo para darle un valor nuevo o dejar que muera).

string s = "hola";
string t = std::move(s);
cout << s;     // ¿""? ¿"hola"? No está garantizado
s = "nuevo";   // esto sí es correcto

El estándar solo promete que un objeto de la biblioteca movido queda «válido pero en estado no especificado». En tu Pila lo dejas vacía a propósito, pero con string o vector no cuentes con nada.

5. Constructor de movimiento y asignación por movimiento

Así quedan las dos piezas para la Pila con nodos:

class Pila {
    Nodo* tope = nullptr;
    int n = 0;
    // ... push, pop, liberar(), regla de tres ...
public:
    // Constructor de movimiento: nace robando
    Pila(Pila&& otra) noexcept : tope(otra.tope), n(otra.n) {
        otra.tope = nullptr;   // ¡imprescindible!
        otra.n = 0;
    }

    // Asignación por movimiento:  a = std::move(b);
    Pila& operator=(Pila&& otra) noexcept {
        if (this != &otra) {   // a = std::move(a) no debe romper nada
            liberar();         // suelta MIS nodos viejos
            tope = otra.tope;
            n = otra.n;
            otra.tope = nullptr;
            otra.n = 0;
        }
        return *this;
    }
};

El error típico: olvidar otra.tope = nullptr;

Entonces dos pilas apuntan a los mismos nodos. Al morir, las dos llaman a su destructor y cada una hace delete de los mismos nodos: el doble delete de la lección 3.5, que suele tumbar el programa. Mover es «llevarte las cosas y dejar al otro sin ellas». Las dos mitades.

¿Y ese noexcept? Promete que la función no lanza excepciones. Importa más de lo que parece: cuando un vector<Pila> se queda sin espacio y tiene que mudar sus elementos a un bloque más grande, solo los mueve si el constructor de movimiento es noexcept; si no, los copia para ir a lo seguro (LearnCpp 27.10 — std::move_if_noexcept). Mover solo roba apuntadores y no puede fallar, así que márcalo siempre.

6. La regla de cinco (y la de cero)

En la lección 3.5 viste la regla de tres. Con el movimiento, son cinco las funciones especiales:

#FunciónSe usa en
1~Pila() — destructoral morir
2Pila(const Pila&) — constructor de copiaPila b = a;
3operator=(const Pila&) — asignación de copiab = a;
4Pila(Pila&&) — constructor de movimientoPila b = std::move(a);
5operator=(Pila&&) — asignación por movimientob = std::move(a);

Regla de cinco: si tu clase necesita escribir una de ellas (porque maneja memoria a mano), piensa en las cinco. Detalle importante: si escribes el destructor o la copia, el compilador deja de generar el movimiento por ti (cppreference — The rule of three/five/zero). No da error: tu std::move simplemente acaba copiando, en silencio.

Regla de cero: lo mejor es no escribir ninguna. Si tu clase guarda sus datos en vector, string o unique_ptr, esos ya saben copiarse, moverse y liberarse, y el compilador genera las cinco bien. Las escribes a mano solo cuando tu clase es la dueña directa de un recurso, como la Pila con new.

7. Por qué devolver un vector grande es barato

Mucha gente que viene de C evita esto «para no copiar»:

vector<int> primos(int hasta) {
    vector<int> r;
    // ... llenar r con miles de números ...
    return r;          // ¿copia miles de números? NO
}
vector<int> p = primos(1000000);

No se copia nada, por dos razones, una detrás de otra:

  1. Elisión de copia. Casi siempre el compilador construye r directamente en el sitio de p: no hay copia ni movimiento. Cuando devuelves un temporal (return vector<int>(10);) está garantizado desde C++17; con una variable con nombre, como r, está permitido y los compiladores lo hacen casi siempre (cppreference — Copy elision).
  2. Movimiento automático. Si no pudo eludirla, un return de una variable local se trata como rvalue: se mueve, no se copia.

Conclusión práctica: devuelve por valor sin miedo. Lo verás en el miniproyecto: crearPila(1000) devuelve una pila de mil nodos y el contador de copias se queda en 0.

No escribas return std::move(r); «para ayudar». Impide la elisión y el resultado es peor. g++ -Wall te avisa: moving a local object in a return statement prevents copy elision [-Wpessimizing-move]. Usa std::move para pasar algo a otro sitio (push_back, una asignación), no en el return.

¿Qué pasa en la memoria?

Mover no mueve ningún nodo. En Pila b = std::move(a); los nodos se quedan quietos en el montón, en la misma dirección. Solo se copian las dos cajas pequeñas del objeto: tope y n. Por eso es O(1). Y a no desaparece: su tiempo de vida sigue hasta el final de su bloque, y entonces corre su destructor. Por eso tiene que quedar con tope = nullptr: así ese destructor no libera nada ajeno. Cuando un vector<Pila> crece pasa lo mismo: muda los objetos Pila (pequeños) al bloque nuevo, y sus nodos no se tocan.

¿Y los objetos de la biblioteca? El estándar en general solo promete que el objeto movido queda «válido pero no especificado». En la práctica, un vector o un string movido suele quedar vacío, porque su bloque del montón se lo llevó el otro; pero no lo uses contando con eso, salvo para darle un valor nuevo. Un detalle: un string corto como "hola" normalmente guarda sus letras dentro del propio objeto, sin montón, y entonces moverlo es copiar esas pocas letras.
