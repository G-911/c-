Polimorfismo

Una sola lista de figuras, y cada una calcula su área a su manera. ~35 minutos.

Al terminar podrás: usar virtual y override para que un Figura* llame al método del objeto real, crear una clase abstracta con = 0, recorrer un vector<Figura*> con figuras mezcladas y liberarlas sin fugas gracias al destructor virtual.

Antes de empezar: repite sin mirar el quiz de la lección 2.5 · Herencia. Dos minutos. Recordar lo de ayer es lo que hace que no se te olvide.

Por qué. La herencia sola ahorra copiar código. El polimorfismo es lo que la hace poderosa: escribes una función para «cualquier figura» y sirve para círculos, rectángulos y para las figuras que inventes el año que viene, sin tocarla. Es el segundo pilar de la POO que te preguntarán en la universidad, y la idea con la que se organizan juegos, interfaces gráficas y casi cualquier programa grande.

1. El problema que dejamos abierto

En la lección 2.5 viste que un apuntador a la base puede apuntar a una hija, porque un círculo es una figura (LearnCpp 25.1):

Figura* p = new Circulo(2);   // vale: un Circulo es una Figura

Eso permite algo muy útil: guardar figuras distintas en el mismo vector.

vector<Figura*> plano;
plano.push_back(new Circulo(1));
plano.push_back(new Rectangulo(3, 4));
plano[0]
Figura* →
objeto Circulo
nombre: "circulo"
radio: 1
plano[1]
Figura* →
objeto Rectangulo
nombre: "rectangulo"
ancho: 3, alto: 4

Pero quedó un problema: sin nada más, p->area() llama a la versión de Figura, porque C++ mira el tipo del apuntador, no el objeto de verdad. Necesitamos lo contrario.

2. virtual: decide el objeto, no el apuntador

Si en la base marcas el método con virtual, C++ cambia de criterio: al llamarlo por un apuntador o una referencia, mira qué objeto hay de verdad en esa dirección y llama a su versión. Y lo decide mientras el programa corre (LearnCpp 25.2).

class Figura {
public:
    virtual string describir() { return "una figura"; }   // virtual
};
class Circulo : public Figura {
public:
    string describir() override { return "un circulo"; }
};

Figura* p = new Circulo();
cout << p->describir();   // un circulo   ← ahora sí
En la base el método es…p->describir() con Figura* p = new Circulo()
normal«una figura» (manda el tipo del apuntador)
virtual«un circulo» (manda el objeto real)

Eso es el polimorfismo («muchas formas»): la misma línea, p->describir(), hace cosas distintas según el objeto.

3. override: que el compilador te vigile

En la hija escribes override después de los paréntesis. No cambia lo que hace el programa: le dice al compilador «esto tiene que reemplazar un método virtual de la base». Si no reemplaza nada, error (LearnCpp 25.3).

El error típico: equivocarse en el nombre o los parámetros.

class Circulo : public Figura {
public:
    string descrbir() { return "un circulo"; }   // falta una «i»
};

Sin override, esto compila sin quejarse: has creado un método nuevo que nadie llama, y p->describir() sigue diciendo «una figura». Puedes perder una tarde buscándolo. Con override, el compilador lo para en el acto: marked 'override', but does not override. Regla: en la hija, siempre override.

4. Clase abstracta: = 0

¿Cuál es el área de «una figura» cualquiera? No existe: solo tienen área los círculos, los rectángulos… Para decir «toda figura tiene área, pero cada hija la calcula a su manera», se escribe un método virtual puro, con = 0 en lugar de cuerpo:

class Figura {
protected:
    string nombre;
public:
    Figura(string n) : nombre(n) {}
    virtual ~Figura() {}                 // sección 6
    string getNombre() { return nombre; }
    virtual double area() = 0;           // virtual PURO: sin cuerpo
};

Una clase con al menos un método virtual puro es abstracta (LearnCpp 25.7):

  • No se pueden crear objetos de ella: Figura f("x"); y new Figura("x") no compilan.
  • Sí se pueden tener apuntadores a ella: Figura* p.
  • Cada hija debe escribir area(). Si una se olvida, también queda abstracta y tampoco podrás crearla.

Así el compilador te obliga a no olvidarte de nada. Las hijas:

class Circulo : public Figura {
private:
    double radio;
public:
    Circulo(double r) : Figura("circulo"), radio(r) {}
    double area() override { return 3.14159 * radio * radio; }
};

class Rectangulo : public Figura {
private:
    double ancho, alto;
public:
    Rectangulo(double an, double al) : Figura("rectangulo"), ancho(an), alto(al) {}
    double area() override { return ancho * alto; }
};

5. Todo junto: un vector<Figura*>

Ahora la recompensa. Una función que suma áreas sin saber ni preguntar qué figuras hay:

double areaTotal(const vector<Figura*>& figuras) {
    double total = 0;
    for (Figura* f : figuras) {
        total += f->area();     // virtual: cada figura usa SU area()
    }
    return total;
}

int main() {
    vector<Figura*> plano;
    plano.push_back(new Circulo(1));
    plano.push_back(new Rectangulo(3, 4));

    for (Figura* f : plano) {
        cout << f->getNombre() << ": " << f->area() << "\n";
    }
    cout << "total: " << areaTotal(plano) << "\n";

    for (Figura* f : plano) {
        delete f;               // cada new, su delete
    }
    plano.clear();
}
// Muestra:
// circulo: 3.14159
// rectangulo: 12
// total: 15.1416

Mañana añades class Triangulo : public Figura con su area(), y areaTotal funciona con triángulos sin cambiar una sola línea. Ese es el gran premio del polimorfismo.

¿Por qué vector<Figura*> y no vector<Figura>? El polimorfismo solo funciona a través de apuntadores o referencias. Un vector<Figura> ni compila (Figura es abstracta), y si Figura no lo fuera, al copiar un círculo dentro se perdería su parte Circulo: se quedaría solo la parte Figura. A eso se le llama slicing, «rebanar» (LearnCpp 25.9).

6. El destructor virtual

Fíjate en el delete f de arriba. f es un Figura*. Con el destructor normal, pasa lo mismo que con describir() en la sección 1: C++ mira el tipo del apuntador y solo ejecuta ~Figura(). El destructor del círculo nunca corre. Si el círculo había pedido memoria con new, esa memoria se pierde. De hecho, el estándar dice que eso es comportamiento indefinido: puede pasar cualquier cosa (LearnCpp 25.4).

Con virtual ~Figura() {}, delete f mira el objeto real: corre ~Circulo() y después ~Figura(), en el orden de la lección 2.5.

Error típico: olvidar virtual en el destructor de la base.

class Figura {
public:
    ~Figura() {}               // MAL: falta virtual
    virtual double area() = 0;
};
Figura* f = new Circulo(1);
delete f;                      // ~Circulo() no se ejecuta

Compila y casi siempre «parece que funciona», por eso es tan traicionero. Por suerte g++ -Wall avisa: deleting object of abstract class type 'Figura' which has non-virtual destructor will cause undefined behavior. Lee los avisos.

Regla fija: si una clase tiene algún método virtual, su destructor también es virtual.

¿Qué pasa en la memoria?

En vector<Figura*> plano hay tres capas. El objeto plano vive en el marco de main; sus casillas (solo direcciones) están en el montón (heap); y cada new Circulo(1) es otra caja del montón, aparte. El vector es dueño de las direcciones, no de las figuras: plano.clear() borra direcciones, y por eso antes hace falta un delete f por figura. Ese delete libera el objeto completo solo si ~Figura() es virtual.

Copiar un Circulo dentro de una variable Figura copia solo la parte Figura: el radio se queda fuera (slicing).

¿Cómo sabe f->area() qué objeto hay? El estándar no lo dice, pero en la práctica los compiladores normalmente usan una tabla por clase (la vtable) y añaden a cada objeto con métodos virtual un apuntador oculto a la tabla de su clase. Por eso esos objetos suelen ocupar un apuntador más (LearnCpp 25.6).
